## 1. 历史 Bug（当前状态以 §8 为准）

### P2 · 状态栏 "Open context tab" 是死按钮

- **复现**：会话详情页（受控 mock 与真实后端均复现；legacy 与 canonical 路由均复现）。点击状态栏右侧 "Open context tab" → 页面零变化：会话 tab（Preview/Context/Artifact）状态不变、review 面板不打开、file tree 不变；连点两次（toggle 路径）同样无效。
- **对比**：timeline 内 "View context usage" 按钮调用**同一函数** `openSessionContext`，点击后 Context tab 正常可见+选中（该路径已被现有 `tab-close-owner.spec.ts` 钉住）。
- **根因方向**：状态栏 `components/status-bar/current-session-source.ts:304` 的 `openContext()` 用自推导 `sessionKey()`（scope = `ServerScope.fromServerKey(activeServerKey())`、目录 = `placement()?.directory`）取 `layout.tabs(key)` / `layout.view(key)`；会话页渲染用的是 `useSessionLayout()`（`session-layout.ts:15-16`，scope = `serverSDK().scope`）。两处 key 任一字节不一致即会新建一个无人渲染的空 store，所有操作落空。尚未用页面内探针最终定位差异字节。
- **证据**：`docs/review/` 本报告附录 A（body 对比：点击前后仅 composer 迟到渲染，tab/review/fileTree 全部零变化）。
- **建议**：下一批用探针对比两处 key 实际值，修 `current-session-source.ts` 的 key 推导复用 `useSessionLayout` 同源。

### P2 · 顶部会话标签关闭后的页面切换不区分活动/后台标签

- 当前 `tabs.tsx:180-199` 关闭任意标签都会导航到其右侧标签，无右侧才到左侧，最后一个标签回全局首页。活动标签的“右 → 左 → 首页”顺序合理，但关闭后台标签也会强制切走当前页面。
- 正确规则：关闭后台标签只移除标签并保持当前页面；只有关闭活动标签才选择后继页面。正式会话仅关闭视图、不删除会话数据，这一点合理。
- 现有 E2E 只覆盖关闭活动标签，缺少 `A/B/C` 中查看 C、关闭后台 A 后仍停留 C 的回归用例。

### P1 候选 · 脏草稿点击 X 可能先删除、后确认

- `removeTab()` 会先移除标签、清理 tab memory/草稿持久化并跳转；`DirtyDraftGuard` 在路由变化后才弹出 Stay/Leave。用户选择 Stay 时可能已无法恢复原标签与草稿状态。
- 应改为关闭前置状态机：脏内容先确认；Stay 不改变任何状态，Leave 后才移除标签与持久化数据。需补“脏草稿 × 顶部 X”实测和回归用例后确认等级。
- 附带 P3：正式 Session 标签的 X 缺少 `aria-label`，而 Draft 标签已有 `Close tab`，无障碍语义不一致。

## 3. 用户反馈与产品改造项（2026-09-10）

> 本节记录用户截图与口述需求。标记为“产品改造”的项目已确认当前交互与目标不一致；标记为“待复现 Bug”的项目尚未完成数据链路和持久化验证，不预判根因。

### 3.1 首页右侧补充固定“新建会话”主按钮（产品改造）

用户截图显示：在“自定义”等无结果筛选状态下，主内容标题行右侧可以看到“新建会话”；但该入口会随空态、筛选结果和会话分组状态改变位置或消失。当前实现还在顶部标签栏、项目行、空态正文提供多个新建入口，导致同一动作缺少稳定的空间锚点；这不是单纯的“用户记忆偏差”。不同端口显示不一致还可能由代码版本、功能开关、本地缓存或返回数据状态不同造成，需在多端口对照时核实。

**目标交互：**

- 首页主内容区域右上方始终显示一个固定的“新建会话”主按钮，不受空态、分组或筛选结果影响。
- 空态中央可以保留引导按钮，但仅作为同一动作的辅助入口。
- 新建动作应继承当前项目和模式筛选；“全部会话”下使用默认模式或进入模式选择，具体语义待产品确认。
- 所有入口必须复用同一新建流程，避免 draft ID、默认模式、Location 或项目上下文出现分叉。

**验收关注：**全部/对话/编程/工作/助手/自定义六种筛选，有无会话、切换项目、刷新和重启后，固定按钮均可见且创建上下文一致。

### 3.2 “添加项目”改为可视化文件夹浏览（产品改造）

现状（`directory-picker.tsx` / `dialog-select-directory-v2`）：用户截图中的“打开项目”弹窗本质是已知/最近物理路径列表与搜索框，目录行不能展开、进入上级或下级目录，也没有面包屑。桌面路径走系统原生目录选择能力，Web/回退路径仍是路径候选器。用户需要的是可浏览的文件夹，而不是阅读或输入物理地址 URL。

**目标交互：**

- 以文件夹树或文件夹网格展示目录，可进入上级/下级目录并通过面包屑返回。
- 只允许选择文件夹；物理路径降为辅助信息，不作为主要操作对象。
- 保留“最近项目”和搜索作为快捷入口，但不能替代目录导航。
- 清楚呈现加载中、空目录、无权限、目录不存在和读取失败状态。
- 首页与五个模式页中的所有“添加项目”入口必须复用同一套可视化目录选择弹窗，不得在 Chat/Coding/Work/助手/自定义模式中退回物理路径或 URL 输入。弹窗的信息架构、文件夹树/网格、面包屑、最近项目、搜索、选中态和错误状态应与本节目标 UI 保持一致；入口只负责提供当前 server/Location、初始目录和是否允许多选。
- 模式页添加完成后，应原子更新项目列表、当前项目及相应模式的数据范围；取消不产生项目记录，重复选择同一目录不重复添加，切换模式后也不能出现不同目录选择实现或状态串扰。

**方案对冲：**

- 简单方案：桌面端继续使用系统原生文件夹选择器，仅统一入口与当前目录提示；优点是稳定、安全、改动小，缺点是 Web 与桌面体验不统一。
- 健壮方案：桌面端通过受权限约束的 main/preload IPC 枚举目录，Web 端通过受限服务端目录枚举能力，App 复用一套目录浏览 UI；必须限制允许浏览的根、阻止符号链接越界并处理权限失败。File System Access API 只作为浏览器能力增强，不作为桌面端主架构。

该项是跨层功能增强，不应简化为更换路径文案或图标。

### 3.3 项目“更多 → 编辑”弹窗的颜色功能异常（待复现 Bug）

用户报告项目列表“更多”菜单中的编辑弹窗存在颜色功能问题。当前尚未记录最小复现步骤，先作为待复现功能缺陷，不猜测是颜色控件、状态同步、接口还是持久化层根因。

**下一阶段验证矩阵：**

- 选择预设颜色后，编辑弹窗内是否即时预览，保存按钮状态是否正确变化。
- 保存后，首页项目行、项目头像/图标、会话列表和其他已打开页面是否同步更新。
- 取消是否完整回滚；刷新和应用重启后颜色是否持久化。
- 浅色/深色主题、自定义色值格式及透明度处理是否一致。
- 连续编辑不同项目是否发生颜色串扰；接口失败时是否错误保留乐观更新。
- 对照 UI store、更新请求/响应和持久化记录，定位单一事实来源及共同根因。

复现后再确定 P1–P3 严重级别、代码位置和修复建议。

### 3.4 首页左侧“项目”移动到“模式筛选”上方（信息架构调整）

当前顺序是“模式筛选 → 项目”。用户建议交换为“项目 → 模式筛选”。该调整符合先选择工作上下文、再筛选上下文内会话类型的用户心智模型，建议采纳：

1. 项目（全部项目、具体项目、添加项目）；
2. 模式筛选（全部会话、对话、编程、工作、助手、自定义）；
3. 会话搜索与结果。

**交互约束：**

- 选择项目后，模式计数按该项目重新计算；切换模式不得清除项目选择。
- “全部项目”才聚合所有项目；项目和模式两个维度应可组合，而不是互相覆盖。
- 当前选择可恢复，但不能跨窗口或跨 Location 污染其他会话上下文。
- 仅交换视觉顺序不够，需验证键盘 Tab 顺序、可访问性阅读顺序和窄屏布局同步改变。

### 3.5 首页全局模式导航与模式筛选的语义边界（关联现有设计）

现状：`layout.tsx` 在首页刻意隐藏 `ModeSwitcher`，该行为由 `home-mode-ownership.spec.ts` 固化，依据 ADR-16（`/` 是独立全局聚合页，模式归 `/mode/:mode`）。用户当前明确提出的是首页项目/模式筛选顺序与固定新建入口，并非要求把首页变成某个模式页。

建议保留首页的全局聚合语义，同时严格区分：

- “模式筛选”只过滤首页会话结果；
- 若后续需要直接进入五个模式详情页，应增加明确的模式导航入口，而不是让筛选按钮同时承担导航；
- 若产品决定改变 ADR-16，应同步修订 ADR 与回归测试，不能把现有测试当作否决新需求的依据。

## 4. 新建会话页专项（2026-09-10 用户反馈）

### 4.1 移除遗留 `opencode` 背景字标，改为当前项目主题名称

- 截图中的大号 `opencode` 来自 `session-new-design-view.tsx` 使用的 `WordmarkV2`；其 SVG 路径仍拼出遗留品牌文字，与 AigcForge 当前品牌及用户所在项目均不一致。
- 用户要求背景展示当前项目主题名称。建议以 `sync().project.name` 为首选，缺失时回退项目目录名；该内容只作低对比度背景水印，不应进入输入框可访问名称或抢占主要阅读层级。
- 项目切换后水印必须响应更新；长名称需要自适应字号、截断或换行，不能溢出输入区。项目数据未就绪时使用 AigcForge 品牌占位，不能闪现 `opencode`。

### 4.2 移除输入框上方“权限档位 / 提议 / 完整”可视控件

- 当前 `SessionComposerRegion` 在所有 PromptInput 前渲染 `PermissionTierSelector`，当模式为 Chat/Work/Assistant 且 agent 为 `meta` 时显示，因此新建页出现独立的“权限档位、提议、完整”区域。
- 用户确认该控件破坏新建页视觉层级，应从新建页面移除。权限策略本身不能删除：仍须由模式与 agent 的既有策略给出安全默认值，并允许在设置、会话详情或真正需要提权时以明确确认流程调整。
- 不应仅用 CSS 隐藏后保留错误状态；新建页首次提交的 `permissionTier`、工具权限和 UI 显示必须保持一致。现有 `permission-tier.spec.ts` 应调整为验证策略数据链路，而非固化该新建页控件。

### 4.3 输入框缺少智能体选择器

- PromptInput 已实现智能体控件，但显示条件为 `settings.visibility.customAgents() && agentOptions.length > 0`；`showCustomAgents` 默认值为 `false`，所以默认新建页看不到智能体列表。这是配置门禁造成的产品默认行为，不是接口中完全没有智能体数据。
- 用户要求新建页直接提供智能体列表。建议：新建页始终显示当前模式允许的主智能体/编排智能体；“显示自定义智能体”设置只控制额外自定义项，不能隐藏整个选择器。
- 列表必须遵循 `ProductModeAgentPolicy`，不能暴露当前模式禁止的 orchestrator；需覆盖加载、空列表、切换模式、切换项目、选择持久化及首次提交携带正确 agent。

### 4.4 项目名称后按条件显示 Git 分支或工作树

- 当前输入框下方项目控件只显示项目名；页面内部另有 Git/worktree 数据源：`sync().data.vcs?.branch`、项目 `worktree` 和 `sandboxes`。用户要求在项目名后补充当前分支或工作树信息。
- 目标格式建议为 `项目名 · 分支名`；当目录属于附加 worktree/sandbox 时优先显示可识别的 worktree 名，并可附分支，例如 `项目名 · worktree-name / feature-x`。
- 仅在 `project.vcs === "git"` 且 branch/worktree 信息真实可用时显示；非 Git、数据加载中或字段为空时完全不渲染占位符、图标或破折号。
- 切换项目、目录或 worktree 后必须即时更新，首次提交必须使用显示内容对应的 directory/worktree，避免 UI 与实际 Session Location 不一致。

### 4.5 新建页上方显示并允许确认/切换当前模式

- 当前 Draft 数据包含 `mode`，但新建页没有模式选择器；模式仅在首页或模式页创建 Draft 时写入。用户确认模式控件应放在输入框上方，替换将移除的权限档位区域，使首次发送前的会话类型清晰可见。
- 首页选择具体筛选后新建时，筛选一次性解析为 Draft 模式：对话→Chat、编程→Coding、工作→Work、助手→Assistant；Custom 没有通用 Draft 路径，必须进入其专属创建流程。
- “全部会话”不是 Session 模式：默认使用最近一次成功新建的模式，首次使用回退 Chat。新建页必须显示最终解析后的实际模式，不能显示“全部会话”。
- Draft 创建后 `draft.mode` 独立持久化；首页后续切换筛选不得静默修改已打开草稿。用户在新建页主动切换模式时，需原子重算 agent 白名单/默认 agent、权限策略、preset/category、可用工具/Skills/工作流及模式文案；保留通用文本和附件，明确重置不兼容配置。
- 首次发送并提升为正式 Session 后冻结模式；如需其他模式，应新建会话。

### 4.6 首页筛选与新建模式的状态分离

- 不得继续用一个全局 `currentMode` 同时表达首页浏览筛选与新建目标。建议明确三份状态：`homeSessionFilter`（首页浏览条件）、`lastNewSessionMode`（“全部会话”下的默认值）、`draft.mode`（草稿模式快照）。
- 首页顶部、项目行、空态及模式页的所有新建入口必须复用同一个 resolver，避免入口不同导致 mode/server/directory/agent/permissionTier 分叉。
- 首页实现当前直接以 `mode.currentMode` 调用 `launchModeSessionOrRoute()`；文档将其视为待重构耦合点，而非稳定持久化设计。

### P1 候选 · 首页切换模式后新建出现 `Cannot connect to API`

- 用户报告在首页选择 Chat/其他模式后新建，会出现 `Cannot connect to API: Unable to connect...`。实测时 4096 与 4444 仍在监听，因此不能直接归因于后端未启动，也不能仅凭错误文案认定为真实网络故障。
- 高概率方向是新建链路的 `mode + server + directory/Location` 组合不一致，或切换项目后只更新 Draft 的 server/directory、未同步模式相关配置。Custom 被源码明确禁止进入通用 Draft 路径，否则首次发送必然失败。
- 该问题与首页模式选择存在相关性，但尚未确认因果。复现时必须记录入口、首页筛选、`draft.mode`、server key、directory/Location、请求 URL/method、底层异常 cause 和 Draft→Session 状态；禁止只修改错误提示掩盖根因。
- 发送前若 mode/server/directory 尚未解析完成，应禁用发送并给出可操作错误；失败后不得产生幽灵 Session、丢失草稿或污染最近模式。

### 4.7 新建页验收组合

- 覆盖 Chat、Coding、Work、Assistant 与 Custom 五种入口，并验证项目水印、模式显示、智能体白名单和权限默认值随模式正确变化。
- 覆盖首页六种筛选（含“全部会话”）、刷新草稿、多草稿标签隔离、首页筛选后续变化和新建页主动切换模式。
- 覆盖 Git 主工作树、Git 附加 worktree、无 Git 项目及 VCS 信息迟到四种状态。
- 覆盖首次发送后的 Draft → Session 提升及失败回滚，确保 mode、project、agent、model、permission、server 和 worktree 一次性原子继承。

## 5. 模式首页需求与评审台账（2026-09-11 至 2026-09-12）

> 本节按 Chat、Coding、Work、Assistant、Custom、横向公共契约和收口决策组织。每个模式的当前事实与目标必须分开阅读；产品讨论不会自动升级实现或验证状态。

### 5.1 Chat 模式首页（CONFIRMED 方向 + CURRENT 缺陷）

#### 5.1.1 产品方向：资产主区 + 左侧会话列表

- Chat 模式暂不改成纯“会话优先”首页：主区域保留提示词、Skills、MCP、命令、智能体、工作流和插件资产工作台，左侧在“功能”列表下方新增“会话”列表，兼顾资产管理与会话快速进入。
- 左侧按“项目 → 功能 → 会话”组织为三个独立区块；项目、功能、会话均支持展开/收起。折叠状态应按用户与工作区持久化，刷新及模式往返后保持；首次进入默认展开当前任务最需要的区块。
- 将当前项目区下方的“新建会话”移动到功能列表之后、会话列表之前，并归属会话模块，形成“会话标题/折叠控制 → 新建会话 → 会话列表”的稳定结构；功能区收起时按钮位置不得上移或改变归属，会话区整体收起时只保留会话标题、状态摘要及新建入口。
- 会话列表至少覆盖当前项目的最近会话、活动/流式状态和当前选中态；点击会话复用现有标签，不能重复创建 Tab。展开大量会话时应分页或虚拟化，且不得重新触发七类资产请求。
- 项目、功能、会话必须具有清晰但不过度的模块范围分割：各区块使用独立标题栏、统一内边距和稳定的上下边界/间距；滚动范围要明确，长项目或长会话列表不能挤压其他模块的标题和核心操作。优先采用分区间距与单条弱分隔线，避免多层卡片和重边框造成视觉噪声。
- 建议项目区按内容上限滚动、功能区按七项完整展示、会话区占用剩余高度并独立滚动；窄屏或低窗口高度下至少保证三个标题栏及“新建会话”始终可达，滚动条不能跨越三区造成归属不清。
- 项目区折叠后仍需保留当前项目名称和切换入口；功能区折叠后保留当前资产类型摘要；会话区折叠后保留活动会话/未读或运行中状态提示。三个区块的折叠按钮需具备 `aria-expanded`、键盘操作和明确名称，并统一展开图标、命中区域及动效。

#### 5.1.2 会话列表仅负责导航，不在右侧内嵌详情

- Chat 首页右侧保持资产工作台职责，不内嵌消息流、输入框、流式输出、工具调用、权限审批或上下文面板，避免与标准 Session 页面形成两套状态和协议链路。
- 点击左侧会话条目直接进入现有标准会话详情路由；整行均应可点击，标题是主要文本而不是唯一命中区域。点击“新建会话”同样进入标准 Draft 新建页。
- 已打开的会话应复用现有顶部 Tab，不得创建重复 Tab；会话的完整运行与交互状态均由标准 Session 页面及其既有数据源负责。左侧列表只显示生成中、等待授权、失败、完成等摘要状态。
- 从会话详情返回 Chat 首页时，恢复此前的项目、资产分类、搜索条件、三个区块的折叠状态及各自滚动位置。恢复状态不能重新触发重复的七类资产请求。
- 关闭顶部 Session Tab 只关闭工作视图，不删除左侧历史会话；会话删除、归档与关闭 Tab 必须保持不同语义。
- 因此产品边界确定为：Chat 首页负责资产管理与会话导航，标准会话详情页负责完整交互执行；不实现“左侧选择会话、右侧联动渲染完整会话”的双栏方案。

#### 5.1.3 已确认缺陷与技术债

- **P2 · 资产行伪交互**：资产行呈现为可点击且支持 Enter/Space，但点击没有详情页、弹窗或反馈。`AssetWorkbenchTable` 已提供 `onSelect`，`ChatAssetWorkbenchMain` 未传入；应接入只读详情/编辑流程，或在未实现前取消按钮语义。位置：`packages/app/src/components/chat/asset-workbench.tsx:313`、`packages/app/src/pages/mode-workspace-slots.tsx:558`。
- **P2 · 搜索条件跨资产类型泄漏**：在 MCP 搜索 `code` 后切换命令，命令列表仍被该条件静默过滤。切换类型时应清空搜索，或按类型分别保存并显式显示过滤状态。
- **P2 · 首次进入重复请求**：主工作台和左侧计数各自并发请求全部七类资产，一次冷加载至少形成 14 次列表请求，随后还会启动 MCP child sync。应归并为单一资源层，计数与列表共享结果及错误状态。位置：`packages/app/src/pages/mode-workspace.tsx:134`、`packages/app/src/components/mode-surfaces.tsx:89`。
- **P2 性能候选 · 大列表无虚拟化**：命令 245、Skills 117、插件 94 均通过 `<For>` 全量渲染；现场切换出现长任务/Jank，INP 一度约 144–208ms。需用固定数据集复测后确定阈值，并为大列表增加虚拟化/分页。
- **P2 · 插件系统来源内部重名**：实测出现 `context7`、`github`、`playwright`、`gitkraken-hooks`、`linear` 等重名条目。当前合并只处理项目与系统之间的同名，不处理多个系统来源；应以稳定的 `source + kind + name` 标识资产，并在 UI 显示来源，不得只按名称粗暴去重。
- **P3 · 空态文案类型错误**：工作流为空、MCP 项目筛选为空时仍显示“暂无已保存的提示词”。空态文案必须使用当前资产类型和当前来源筛选。

#### 5.1.4 本轮通过项与边界

- 七类入口均可加载；搜索与“全部/项目/系统”过滤本身可生效。
- Chat 左侧“新建会话”已验证创建 `mode=chat` Draft；未发送消息、未消耗模型额度，测试空草稿已清理。
- 本轮未创建、导入、删除或修改真实资产；相关写操作、失败回滚和并发冲突留待受控数据专项验证。

### 5.2 Coding 模式首页（真实观察 + PROPOSED）

本轮使用 Codex 内置浏览器真实查看 `/mode/coding`：左侧显示多个项目，每个项目都有“新建会话”和“更多选项”；右侧显示会话搜索、按时间分组的会话列表和另一个“新建会话”。当前结构可支持基本会话导航，但存在以下未定义项：

- 项目列表究竟是选择器、树还是项目管理器；项目、worktree、server 的层级、展开/收起和选中语义未在此前讨论中明确。
- 同一项目的新建入口在左侧项目行和右侧列表中重复，必须使用同一 resolver，并明确各入口是否完全等价。
- 右侧会话列表缺少运行中、等待授权/输入、失败、中断、分支/worktree 等对编码用户关键的摘要状态。
- 没有定义无会话、无项目、仓库失效、Git 信息迟到、项目离线、会话分页/虚拟化和加载失败的恢复体验。
- 项目切换后搜索、滚动和会话选择如何保存；关闭 Session Tab 后回到哪个项目/筛选状态；跨 worktree 同 ID/同标题如何区分，均未闭环。

推荐保留 Coding 的合理例外：**左侧项目树、右侧会话索引**，不为了形式统一而在左侧再复制一份完整会话列表。目标契约：

- 左侧按 server → 项目 → worktree/sandbox（仅真实存在时）表达层级，支持独立展开/收起、搜索和状态；点击箭头只展开，点击行才切换当前 Location。
- 右侧顶部显示当前项目、路径、分支/worktree和唯一主“新建编码会话”；随后是搜索/状态筛选、继续工作、当前项目会话列表。
- 左侧项目行可保留快捷“新建”，但必须与右侧主按钮调用同一创建事务；若无法保证语义一致，则只保留右侧主按钮，项目行进入更多菜单。
- 会话列表至少显示 Agent、分支/worktree、更新时间和运行中/等待授权/等待输入/失败/完成；点击直接进入 canonical Session。
- 切换项目清除上一项目会话数据并显示 loading，不得闪现；返回时恢复每个 Location 的搜索和滚动。
- 项目删除/移除只解除应用关联，不删除物理仓库；当前 Location 被移除时必须选择确定性的后继项目或显示无项目引导。

在完成 Coding 目标实现与真实操作前，不能宣称 Coding 首页已完成或已通过验收。

### 5.3 Work 模式首页（CONFIRMED 方向 + OPEN 架构边界）

> 本节是当前 E2E 走查分支中的产品需求台账，不代表功能已经实现，也不直接改写权威 PRD、页面架构或 ADR。尤其是“用户自建工作预设”会改变现有 Chat/Work 资产边界，实施前必须单独完成架构裁决。

#### 5.3.1 测试边界与首页定位

- 当前仅验证 `/mode/work` 在 Codex 内置浏览器可达，项目栏、添加项目、新建会话和四类预设可见；受控 E3 覆盖 loading、资源 500 隔离及 Retry。尚未完成 Work 首页所有内容的真实用户操作测试，不能称为“Work 首页已完整测试”。
- 当前可用官方预设为“撰写 PRD”“视频分镜脚本”“文献对比综述”“撰写行政公文”；其他卡片显示“即将上线”。四个可用预设的完整澄清、创建、执行、产物保存与恢复尚未逐项走通。
- Work 首页应定位为**工作台与任务分流入口**，不是预设详情页、澄清问卷页或 Session 详情页。真实用户进入首页首先要确认：当前在哪个项目、哪些工作需要继续、接下来是继续已有工作还是开始新工作。
- 首页原则为“先继续工作，再开始新工作”。首页负责定位和分流；预设详情、澄清、最终确认、模型执行及 Progress Ledger 进入后续流程。

#### 5.3.2 左侧目标布局：项目、工作预设、会话

左侧与 Chat 模式保持一致的三段式信息架构，三个分组可独立展开/收起，不采用互斥手风琴：

1. **项目**：显示当前项目/Location，支持切换和添加项目；展开后显示项目树。切换项目后右侧回到该项目的工作台概览。项目树究竟采用多项目、目录树还是 workspace/worktree 层级，实施前必须复用现有 Location 模型裁决，不能另建项目模型。
2. **工作预设**：展示官方预设分类，同时增加“我的预设”和“创建预设”；左侧只显示名称、分组和状态，不承载长说明或完整卡片。官方分类至少包括 IT 研发、视频创作、学术科研、行政通用，并支持二级折叠。
3. **会话**：展示当前项目最近的 Work 会话，至少包含名称、所属预设、更新时间以及草稿/运行中/等待输入/完成/失败状态。点击具体会话直接进入 canonical Session，不增加“详情—再打开”步骤；“查看全部”进入独立会话管理视图。

统一交互约束：

- 分组展开/收起不改变右侧当前内容；只有选择项目、预设分类、管理入口等明确导航操作才改变右侧。
- 使用 `aria-expanded`、`aria-controls` 和键盘操作，标题高度、箭头、命中区域、焦点样式与 Chat 左栏一致。
- 展开状态按 `server + workspace + mode` 持久化，Work 与 Chat 互不覆盖；首次进入默认三组展开。
- 项目区和预设区限制高度，会话区占用剩余空间并独立滚动；窄屏或低高度下仍保证三个标题和主要操作可达。
- 首页只保留一个语义明确的“新建工作”主入口，避免当前“新建会话”重复出现且含义不清。

#### 5.3.3 右侧目标布局：工作台概览

右侧首页按以下顺序组织，不再由完整预设卡片墙占满首屏：

1. **当前工作区**：紧凑显示项目名称、路径、Git 分支或 worktree、连接/路径状态，并提供“切换项目”“新建工作”。
2. **继续工作（第一主区）**：展示最近 3–5 个 Work 会话，以及所属预设、更新时间和状态；按状态提供“继续填写”“查看进度”“重试”“打开结果”等直接操作。无历史时显示可操作空态，引导选择或创建预设。
3. **开始新工作**：首页只展示最近使用、推荐预设和分类入口，并提供“查看全部预设”“创建预设”。卡片仅显示名称、一句话用途、预计产物、步骤/澄清问题数量和可用状态。“即将上线”必须真正 disabled，不可点击且不进入键盘 Tab 顺序。
4. **最近产物**：在首页下部展示最近生成的产物、所属会话、更新时间以及“打开/继续编辑”。只有既有 Artifact 模型能稳定供数时才实现，不得为首页另造一套产物真源；条件不具备时仍从对应 Session 访问。

以下内容不直接铺在首页：完整预设说明、适用/不适用场景、澄清问题、回答摘要、输出路径与权限确认、模型生成过程、Progress Ledger、完整对话，以及完整预设/会话管理表格。

页面流转保持单一职责：

```text
Work 首页
├─ 历史会话 ─────────────→ canonical Session
├─ 可用预设 ─────────────→ 预设详情与任务创建流程
├─ 创建预设 ─────────────→ 用户预设创建流程
├─ 我的预设/查看全部 ─────→ 预设目录与管理
├─ 查看全部会话 ─────────→ 会话管理
└─ 最近产物 ─────────────→ 对应 Session 的产物视图
```

#### 5.3.4 新增需求：用户自建工作预设

- 用户可以把反复执行且已验证的工作方法创建为 **Work 专用预设**，以后从 Work 首页直接复用，不必理解或手工组装 Agent、Skill、MCP 和 Prompt。
- 预设是可复用的任务入口与执行配置；Session 是使用某个预设产生的一次执行记录。编辑预设默认只影响后续 Session，历史 Session 保留其所用预设 ID、版本及必要快照。
- 创建入口包括：左侧“工作预设 → 创建预设”、右侧“开始新工作 → 创建预设”、完成 Session 后“存为预设”。三个入口进入同一独立流程，首页不嵌入完整编辑器。
- 创建流程至少覆盖：基本信息、适用/不适用范围、所需输入与澄清问题、执行说明、输出格式/命名/Location 相对保存位置、能力与权限、预览与隔离试运行、保存草稿/发布。
- “我的预设”至少支持搜索、分类、状态筛选、最近使用排序、新建、编辑、复制、停用/启用、归档/删除，并显示草稿/可用/停用/缺失依赖状态。
- 官方预设不可被用户直接覆盖，可复制为用户预设后修改；同名时必须明确标记官方/用户来源。删除用户预设不得破坏已有 Session 和产物。
- 首期至少考虑个人预设（跨项目可见）和项目预设（当前项目/Location 可见）。团队共享、导入导出和市场不阻塞首页首期，但正式数据契约应预留 owner、scope、version、schema version。

安全与持久化约束：

- 预设不得持久化明文密钥、访问令牌或临时授权结果，只能引用既有安全存储中的凭据身份。
- 从 Session 存为预设时，默认排除对话正文、个人信息、项目绝对路径、产物正文和任务特定数据，再由用户确认可复用字段。
- 预设中的保存位置保持 Location 相对语义，不能固化其他项目的绝对路径。
- 预设发布或能力变化后，执行仍必须经过既有 Permission 机制；导入或共享的预设按不受信任内容处理。
- 试运行使用隔离测试数据，不能污染正式会话、最近工作和正式产物。
- 保存、发布或 Session 创建失败时必须保留用户已填内容，并允许重试。

#### 5.3.5 与现有架构边界的冲突

现有 Work 文档将 Work 定义为消费官方硬编码预设或 Chat 资产，且不在 Work 内创建可复用资产；“用户自建工作预设”与该边界存在直接冲突。本轮只在 E2E 报告登记需求，不提前修改权威 PRD、`docs/architecture/pages/work.md` 或 ADR。

实施前需完成以下裁决：

- Work 专用预设是独立产品对象还是现有 Workflow/Asset 的受限视图；
- 如何复用既有资产身份、版本、权限、作用域和持久化能力，避免平行基础设施；
- Work 负责简化创建与日常管理，Chat 是否继续负责跨模式、团队级 Workflow 的高级编辑和治理；
- 官方预设、个人预设、项目预设及未来团队预设的继承、复制、重名和版本升级规则。

在裁决完成前，不得用 localStorage、临时 JSON 或仅前端状态冒充正式用户预设能力。

#### 5.3.6 后续真实用户 E2E 门禁

实施后必须继续使用 Codex 内置浏览器，以真实操作而非只做 route mock 验证：

- 左侧三组的鼠标、键盘、折叠持久化、独立滚动和项目联动；
- 右侧当前工作区、继续工作、开始新工作、最近产物及 loading/empty/error/retry；
- 切换项目后，会话、项目预设和产物同步切换，不能泄漏上一项目数据；
- 四个官方预设逐一完成详情、澄清、返回、取消、刷新恢复、最终确认、Session 创建、真实执行和产物保存；
- 至少一个用户预设完成新建、草稿恢复、隔离试运行、发布、启动 Session、编辑、复制、停用和归档/删除；
- “即将上线”卡片的鼠标和键盘 disabled 行为；
- 无项目、路径失效、缺失依赖、权限拒绝、创建失败、冲突、重试、长任务和中断恢复；
- 窄屏、键盘与基础无障碍行为。

在上述真实链路完成前，`/mode/work` 继续保持 `PARTIAL`，不得将页面可达、内容渲染或受控异常测试描述为“Work 首页所有内容已完成真实用户 E2E”。

### 5.4 Assistant 模式首页（CONFIRMED 方向 + OPEN 项目能力）

> 本节是当前 E2E 走查分支中的产品需求台账，不代表功能已经实现，也不直接改写权威 PRD、页面架构或 ADR。当前真实页面只验证了可达与可见结构，尚未完成提醒、记忆、知识库、项目切换和真实会话的完整用户链路。

#### 5.4.1 当前真实用户观察

- 当前 `/mode/assistant` 左侧显示项目 `cc`、添加项目、新建会话，以及“知识”分组下的提醒、记忆、知识库、悬空链接；右侧固定显示“助手仪表盘”、提醒和知识库空态。
- 左侧处于项目 `cc`，右侧却描述“提醒、收件箱与个人会话”，个人与项目作用域冲突；用户无法判断提醒、记忆、知识和会话保存在哪里、属于谁以及切换项目后的行为。
- “知识”不能准确概括提醒和记忆；“悬空链接”过于技术化，应作为“知识问题”的一种类型，而不是普通用户一级入口。
- 当前首页缺少个人助手物理目录的首次配置、数据边界说明、最近会话、记忆摘要、知识健康和明确的左右联动。

#### 5.4.2 项目树标题中的“个人 / 项目”范围 Tab

助手模式左侧仍采用“范围项目树 → 助手能力 → 会话”三段式可折叠结构，但在项目树模块标题中加入两个固定 Tab：`个人`与`项目`。这两个 Tab 是数据范围选择器，不是“每个项目一个横向 Tab”。

```text
项目范围                         [折叠]
[个人] [项目]                    [范围操作]

个人：唯一的个人助手物理目录
项目：用户已添加的物理项目列表/项目树
```

##### 个人 Tab

- 首次尚未配置时，下方显示“创建个人助手文件夹”和“选择已有文件夹”的引导，不显示假装可用的空仪表盘。
- 用户选择或创建一个真实物理目录，作为唯一的个人助手根 Location，用于承载个人知识、可管理记忆、助手会话及与提醒关联的用户数据。
- 完成后显示“我的助手”、真实路径和目录健康状态；支持打开目录、重新关联及明确的迁移流程。
- 个人助手不是内存虚拟作用域，也不应仅依赖隐藏数据库。移除关联或更换目录绝不能删除用户磁盘文件。
- `个人`范围不存在普通“添加项目”语义；未配置时范围操作是创建/选择个人空间，已配置后改为目录设置。

##### 项目 Tab

- 下方显示用户通过统一“添加项目”流程添加的物理项目列表；可选择项目并按需展开当前项目树。
- 添加入口只添加或关联物理目录；从列表移除只解除应用关联，不删除磁盘目录。
- 列表显示项目名，完整路径通过次级文本、详情或 tooltip 呈现；项目较多时支持搜索、滚动或虚拟化。
- 选择具体项目后，助手能力、会话列表和右侧内容全部切换到该项目范围；未选择项目时显示项目选择空态，不能回退到个人数据。

##### 统一交互

- 点击`个人/项目` Tab 会切换数据范围；点击整个模块的折叠箭头只改变左侧可见性，不改变范围和右侧。
- 点击项目目录箭头只展开目录；点击“我的助手”或具体项目名称才选择 Location 并联动右侧。
- 两个范围分别保留上次选中的目录/项目、列表滚动和能力入口；切回时可恢复，但不能恢复失效或无权限的详情。
- 范围 Tab、项目树、助手能力、会话均满足键盘操作、可见焦点、`aria-expanded`/`aria-controls`及清晰的选中状态。

#### 5.4.3 助手能力与会话列表

- 第二组由“知识”改为**助手能力**，包含提醒、记忆、知识库、知识问题；“悬空链接”降级为知识问题中的问题类型。
- 第三组为**会话**；“新建会话”归属于该组，列表显示当前范围的最近助手会话、更新时间及运行中/等待输入/完成/失败状态。
- 三个模块可独立展开/收起，折叠不改变右侧。能力区与会话区的数据源必须跟随`个人/项目 + 当前 Location`切换。
- 点击能力名称切换右侧管理页；点击“会话”标题或“查看全部”显示当前范围的会话管理；点击具体会话直接进入 canonical Session，不在首页右侧复制消息流。

#### 5.4.4 右侧联动契约

右侧页面由三层状态唯一决定：

```text
个人/项目范围 Tab × 个人目录或具体项目 × 当前助手能力/条目
```

统一规则：

1. 切换`个人/项目`或具体项目时，立即清除上一范围内容并回到新范围的仪表盘；加载期间显示骨架，不能短暂泄漏上一范围数据。
2. 折叠左侧分组不改变右侧；选择能力或具体条目才改变右侧页面。
3. 右侧顶部始终显示范围、Location 名称、物理路径，以及项目场景下真实可用的 Git 分支/worktree，避免用户误判数据归属。
4. 右侧创建操作继承当前 Location；跨个人与项目读取必须显式授权，不能默认共享个人提醒、记忆或知识。
5. 浏览器返回应恢复上一范围、能力、筛选和有效条目；具体会话仍进入标准 Session 路由。

##### 个人首次未配置

右侧显示完整 onboarding：个人助手空间用途、创建新文件夹、选择已有文件夹、数据保存和权限说明、最终路径确认。创建失败保留选择并允许重试。

##### 个人助手仪表盘

默认展示：

- **需要处理**：逾期/今日提醒、等待输入或失败的助手任务、知识问题；
- **继续会话**：最近 3–5 个个人助手会话；
- **最近更新**：最近记忆与知识；
- **快捷操作**：新建会话、创建提醒、添加知识、打开助手目录；
- **空间状态**：物理路径、可用性、索引与最近同步状态。

##### 项目助手仪表盘

选中具体项目后默认展示：

- 项目名称、物理路径、Git 分支/worktree和项目助手启用状态；
- 最近项目助手会话；
- 项目知识、项目记忆与知识健康；
- 项目范围待处理事项和快捷操作；
- 引用个人助手知识的显式授权入口，而不是默认混入个人数据。

普通项目首期明确支持项目会话、项目知识库、项目记忆和项目知识问题。项目提醒是否开放需由后续数据作用域设计裁决；在无可靠项目提醒模型前，不得将个人提醒复制或伪装成项目提醒。

##### 能力管理页

| 左侧能力          | 右侧内容                                                              |
| ----------------- | --------------------------------------------------------------------- |
| 助手能力标题      | 当前范围的助手仪表盘                                                  |
| 提醒              | 当前范围的今日/逾期/即将到期/已完成提醒及创建、修改、完成、暂停、删除 |
| 记忆              | 可查看来源和作用域、可编辑/删除/纠正的记忆列表                        |
| 知识库            | 当前 Location 的知识文件、来源、搜索、导入、索引状态与打开目录        |
| 知识问题          | 失效引用、悬空链接、索引失败、冲突、缺失权限及修复/忽略/重新关联      |
| 会话标题/查看全部 | 当前范围的会话管理列表                                                |
| 具体会话          | canonical Session                                                     |

#### 5.4.5 数据与安全边界

- 个人助手必须绑定用户确认的真实物理目录；提醒调度数据库可以作为执行索引，但不能成为用户数据唯一且不可见的真源。
- 普通项目不自动扫描整个目录，不默认继承个人助手数据；首次启用项目知识、记忆等能力时应说明索引范围、写入位置和权限。
- 个人与项目之间的任何跨 Location 读取均需显式授权，并继续遵循现有 Permission 机制。
- 切换、移除、重新关联或索引失败不得删除原始文件；路径失效时提供重新关联，而不是静默创建新空间。
- 右侧所有摘要、左侧计数与正式管理页必须复用同一数据源，不能维护第二套提醒、知识或 Session 状态。

#### 5.4.6 后续真实用户 E2E 门禁

实施后继续使用 Codex 内置浏览器验证：

- 个人首次创建目录、选择已有目录、取消、失败重试、刷新恢复和重新关联；
- `个人/项目` Tab 的鼠标、键盘、状态恢复、范围切换和数据不串线；
- 添加、选择、展开、移除及路径失效的物理项目；
- 三段式分组折叠、独立滚动、窄屏及无障碍；
- 个人和项目范围下提醒、记忆、知识库、知识问题的列表、详情、创建、修改和失败状态；
- 点击具体会话进入 canonical Session，以及新建会话对当前 Location 的正确继承；
- 跨 Location 引用的授权、拒绝和撤销；
- 切换范围时无旧数据闪现，浏览器返回恢复正确上下文。

在上述真实链路完成前，`/mode/assistant` 保持 `PARTIAL`，不得把首页可达、固定空态渲染或受控 route-shell 测试表述为助手首页完整 E2E。

### 5.5 Custom 模式中心与用户模式（CONFIRMED 模型 + PROPOSED 架构）

> 本节是当前 E2E 走查分支中的产品需求台账，不代表功能已经实现，也不直接改写已接受的 ADR-17、Custom PRD 或页面架构。实现前应以 ADR-17 的稳定协议边界为基础完成正式产品与架构修订，不能动态扩展核心 `ProductMode`，也不能用仅前端状态冒充可持久化的用户模式。

#### 5.5.1 当前真实用户观察

- 当前 `/mode/custom` 进入后直接同时展示项目资产浏览器、临时组合编辑器、启动区和诊断区，没有独立的模式中心首页。
- 左侧标题为“项目资产”，实际却混入大量 `agents-*`、`zcode-*`、`claude-*` 等系统或外部来源命令，标题与真实作用域不一致。
- 命令达到 243 项并默认形成超长列表，淹没智能体、工作流、提示词和技能等主要创建路径；浏览资产和修改组合没有清晰边界。
- 页面直接暴露“使用方绑定”“orchestrator”“临时组合”“Composition Plan”等内部概念，普通用户无法形成稳定心智。
- 实测曾出现诊断显示“组合计划检查通过”，同时启动按钮禁用；MCP 页又报告 Agent revision 为空。诊断、启动门禁和面板状态不是同一事实源，不能据此判定组合可运行。
- 当前页面更接近内部组合调试器，不满足终端用户“打开已有模式、继续草稿、创建、测试、发布、运行、升级和归档模式”的闭环需求。

#### 5.5.2 产品收敛：一个模式中心，N 个用户模式

Chat、Custom 和用户模式的职责收敛为：

```text
Chat：创建、编辑和管理智能体、工作流、提示词、技能、命令、MCP、插件等模块
Custom（面向用户命名为“模式中心”）：组装、测试、发布和管理用户模式
用户模式：由已发布 Custom Profile/Release 提供的独立运行体验
```

不再新增一个与 Custom 重叠的第六个固定产品模式，也不把每个用户模式动态加入核心 `ProductMode` 枚举。产品体验允许用户创建 N 个模式；底层保持稳定：

```text
ProductMode = custom
Mode/Profile ID = stable-profile-id
Mode Release = immutable release revision
Composition Snapshot = Session 启动时冻结的实际运行真值
```

模式改名不改变稳定 ID；已发布版本不可原地修改；新 Session 使用当前活动 Release；运行中和历史 Session 始终保留各自 Snapshot。停用、归档或删除模式不得破坏历史 Session、产物与审计事实。

#### 5.5.3 统一产品语言：模块、电路板与强类型插槽

为降低用户理解成本，模式中心采用“插拔模块”的产品模型：

| 用户概念   | 系统语义                                 |
| ---------- | ---------------------------------------- |
| 模块       | Chat 资产及其明确 revision               |
| 模式电路板 | 用户模式 Draft 或不可变 Release          |
| 插槽       | 资产类型、消费者、数量和兼容性约束       |
| 插入/拔出  | 在草稿中新增/移除显式 Binding            |
| 电路检查   | Composition Plan、依赖、权限和兼容性诊断 |
| 测试运行   | 隔离测试 Session                         |
| 发布       | 生成不可变 Mode Release 并切换活动版本   |
| 正式运行   | 基于 Release 创建 Session Snapshot       |

用户只需要理解“选择模块并插到合适位置”；底层仍保存结构化绑定、稳定身份和版本，不能只在前端绘制连接关系。

标准插槽包括：

1. **主执行者**：兼容的用户 Agent；
2. **协作智能体**：可选的额外 Agent；
3. **工作方式**：可选 Workflow；
4. **指导模块**：Prompt；
5. **专业能力**：Skill；
6. **快捷工具**：Command；
7. **外部连接**：MCP；
8. **运行扩展**：Plugin；
9. **模式首页组件**：快捷任务、输入表单、产物入口等平台组件。

插槽必须强类型：Prompt 不能进入 MCP 插槽，Command 不能成为 Agent。默认界面通过模块所在层级自然表达“由谁使用”，例如把 Skill 插入某个 Agent 下的“专业能力”槽，不再要求普通用户理解 `consumer = agents/security-reviewer`。多消费者、步骤级绑定和条件启用可放入高级连接视图，但基础插槽和高级视图必须操作同一份 Binding，不能形成两套配置。

#### 5.5.4 最小可测试、可发布范围

**不得要求填满所有标准插槽才能测试或发布。**插槽是可组合能力，不是固定表单清单。系统采用“最小可运行电路 + 按已插入模块增量校验”的门禁。

##### 最小必要内容

一个模式草稿达到以下条件即可进入真实隔离测试：

- 稳定模式身份及非空名称；图标、颜色和说明可以采用平台默认值；
- **至少一个可解析、兼容且有明确 revision 的主执行者 Agent**；平台固定的 `meta` 根编排器不替代该用户执行模块；
- 至少一个平台默认运行入口。若用户未配置 Workflow 或首页快捷任务，平台提供“自由输入并启动”的默认入口；
- 明确的运行 Location/作用域，且没有路径、身份或 revision 冲突；
- 当前已插入模块不存在 blocking 诊断。

因此最小电路可以是：

```text
模式名称 + 主执行者 Agent + 平台默认输入入口
```

Workflow、Prompt、Skill、Command、MCP、Plugin、协作 Agent、自定义首页组件均为可选。未插入的可选槽不产生警告，也不阻止测试或发布。

##### 条件性必要内容

只有当用户选择相关能力后才成为门禁：

- 插入 Workflow 后，所有步骤、入口和被引用 Agent 必须可解析；
- 插入 MCP 后，其 server、凭据引用、连接状态和权限请求必须可解释；
- 插入 Plugin 后，必须满足安装、校验、信任、版本和运行时策略；
- 添加首页快捷任务后，每个入口必须指向有效 Workflow、Prompt 或默认会话入口；
- 添加文件写入、Shell、网络等能力后，必须显示权限差异并继续受运行时 Permission 裁决；
- 引用项目资产后，模式运行 Location 必须兼容，或在启动前显式完成跨 Location 授权。

##### 测试和发布门禁

- **电路检查**不调用模型，检查必需槽、引用、Binding、Workflow 图、工具、权限上限和版本一致性。
- **隔离测试**只要求最小电路成立，不要求填满可选槽；测试数据、会话和产物不能污染正式历史。
- 发布要求最小电路至少完成一个成功的隔离 smoke 场景、发布差异可读、没有 blocking 诊断；警告可以经用户确认后发布。
- 权限扩大、主执行者、Workflow、MCP 或 Plugin 变化时必须重新测试；仅修改名称、说明、颜色等展示字段可进行轻量检查，不强制重新执行模型测试。
- 发布按钮附近必须列出所有阻塞原因；“诊断通过”必须与“可测试/可发布”使用同一状态机和事实源。

#### 5.5.5 模式中心首页：左右内容列

模式中心首页保持两列，不在默认首页嵌入专业 Builder：

```text
全局模式导航 │ 模式中心左栏 │ 模式中心首页主区
```

只有点击“创建模式”“继续编辑”“修复”或“编辑下一版本”后，才进入电路板 Builder。

##### 左侧第一组：项目

- 显示当前项目、真实物理路径和可用的 Git 分支/worktree；支持添加、切换和展开项目树。
- 项目树展开/收起只改变左栏，不改变右侧；切换项目后右侧回到新项目的模式中心概览。
- 切换时重新加载模式、资产摘要和会话，不得短暂显示上一项目数据。
- 模式必须标明个人/项目作用域和来源项目。现有 Profile 若仍仅支持项目目录，UI 必须明确显示“项目模式”，不能伪装成全局个人模式。

##### 左侧第二组：模式

```text
模式
├─ 全部模式
├─ 已发布
├─ 草稿
├─ 需要处理
├─ 模式模板
├─ 模块库
└─ 创建模式
```

- “需要处理”统一收纳未保存恢复项、发布失败、缺失模块、版本漂移、MCP/Plugin/凭据异常和待确认升级。
- 可在分类下显示少量模式名称、图标、状态与更新时间；点击模式打开右侧概览，不直接进入编辑器。
- `模块库`是对 Chat 资产注册表的只读选择/影响视图；资产正文编辑仍回到 Chat。
- 模式数量较多时使用搜索、分页或虚拟化，不在左栏平铺全部配置。

##### 左侧第三组：会话

- 展示当前范围最近的 Custom Session、所属用户模式、更新时间以及运行中/等待输入/完成/失败状态。
- 点击“会话”标题或“查看全部”打开右侧会话管理；点击具体会话直接进入 canonical Session。
- “新建模式会话”继承当前已发布模式；未选择模式时先选择可运行 Release。
- 会话区占据剩余高度并独立滚动。三个左侧分组可独立折叠，折叠不改变右侧。

##### 右侧默认首页

按真实用户优先级显示：

1. **当前工作区**：项目、路径、分支/worktree、个人/项目模式数量，以及“创建模式”“导入配置”；
2. **需要处理**：仅在存在问题时显示，包括草稿恢复、发布失败、缺失模块、版本漂移、MCP/凭据问题和等待输入/失败 Session；
3. **继续编辑**：已保存草稿、未保存恢复项、当前阶段、缺失步骤和“继续/修复/丢弃”；
4. **我的模式**：最近使用、已固定和最近发布的模式，显示作用域、活动版本、健康、固定状态及“打开/启动/编辑/固定”；
5. **快速创建**：从最小空白电路、模板、已有模式复制、Chat 模块和配置导入开始；
6. **模块准备情况**：按 Agent/Workflow/Prompt/Skill/Command/MCP/Plugin 显示数量、来源和异常摘要，不展开 243 条命令；
7. **最近会话**：模式、状态、更新时间，以及继续、查看结果或重试。

首次没有模式时，“快速创建”升级为首屏 onboarding，解释 Chat 模块与用户模式的关系，并提供“最小模式”“从模板”“使用 Chat 模块”三个入口。当前项目缺少必要 Agent 时应提供“前往 Chat 创建 Agent”，返回后保留模式草稿。

##### 点击具体模式后的右侧概览

模式概览至少显示：模式说明、作用域、活动 Release、是否固定、首页预览、已插入模块摘要、权限与依赖健康、最近会话，以及“打开模式首页”“新建会话”“测试”“编辑下一版本”。概览是只读决策页，不因点击模块或模式名称隐式修改配置。

#### 5.5.6 电路板 Builder：三列布局与交互

进入创建或编辑后采用三列：

```text
模块库                 模式电路板                   检查与属性
搜索/类型/来源/状态     必需与可选强类型插槽          模块详情/权限/差异/诊断
```

##### 左列：模块库

- 类型：Agent、Workflow、Prompt、Skill、Command、MCP、Plugin；
- 来源：当前项目、个人、系统内置、插件、未来团队共享；
- 状态：可插入、已插入、有更新、缺失依赖、只读、解析失败；
- 使用情况：当前模式使用、其他模式使用、已发布版本锁定、运行中 Session 使用；
- 搜索名称、说明、路径、标签、能力和提供者；默认优先当前项目、最近使用、兼容且健康的模块。

只预加载摘要，点击后再加载正文、依赖和引用；单类加载失败不能清空其他类型，也不能把请求失败显示成“未发现模块”。长列表必须分页或虚拟化。

##### 中列：模式电路板

- 显示模式名称、当前草稿基线、最小电路完整度、必需模块、可选插槽和未保存状态；
- 点击模块先预览，不改变草稿；只有“插入兼容插槽 → 选择目标 → 确认”才建立 Binding；
- 拔出模块只移除草稿引用，不删除 Chat 资产，并支持撤销；
- 未插入可选槽保持安静，不用空警告制造“必须填满”的错觉；
- 普通视图使用自然语言层级，高级连接视图才显示多消费者和步骤级绑定。

##### 右列：检查与属性

- 当前模块详情、来源、owner、revision、只读原因和反向引用；
- 当前插槽兼容性、Binding 目标和配置属性；
- 电路检查、权限与工具差异、MCP/Plugin/凭据健康；
- 相对活动 Release 的模块、权限和首页变化；
- 测试结果、发布阻塞与修复入口。

窄屏顺序为“电路板主视图 → 模块库抽屉 → 检查抽屉”，不能把三列压缩到互相遮挡。

#### 5.5.7 Chat 模块库读取、绑定与反向引用

模式中心不复制 Chat 资产正文，而应读取同一 typed registry/统一 Asset Catalog Read Model，通过稳定引用绑定：

```text
assetID + asset revision + binding target + scope/source
```

短期若继续使用 `kind + relativePath + revision`，必须登记重命名/移动导致引用脆弱的技术债；长期需要稳定 `assetID` 和不可变 revision 存储。

##### Chat 资产库增加使用情况

Chat 资产列表显示紧凑引用摘要，例如“被 3 个模式引用 · 2 个发布版本锁定”。资产详情增加“引用关系”，至少展示：

- 用户模式名称、作用域、草稿/已发布/停用状态和模式版本；
- 插入到哪个 Agent、Workflow 步骤或模式级插槽；
- 当前引用的资产 revision 与最新 revision；
- 是否存在可升级版本、缺失依赖和运行中/历史 Session；
- “打开模式”“比较版本”“在模式中心评估升级”。

被引用后的资产不应整体锁死。规则是：

> **锁定已发布模式引用的模块版本，不锁死模块自身的演进。**

- 用户资产在 Chat 中编辑并保存为新 revision；草稿和已发布模式继续引用旧 revision，直到用户显式采用；
- 已发布 Release 与 Session Snapshot 永不自动升级；
- 系统/插件只读模块因来源只读，而不是因为被模式引用才只读；
- Chat 编辑前显示影响说明：哪些模式将出现“有更新”，并明确当前运行 Session 不受影响；
- 资产删除前查询反向引用。存在发布/历史引用时默认归档，不物理破坏旧 revision；归档模块不再供新模式插入，但历史引用和审计继续可见。

若历史 revision 被新内容覆盖后不可读取，已发布模式就无法稳定创建新 Session。因此正式发布闭环必须具备不可变 Asset Revision Store，或等价的不可变 Release Bundle；推荐内容寻址的 revision store，避免每个模式重复复制正文。

#### 5.5.8 检查、测试、发布和运行闭环

```text
Chat 创建模块
→ 模式中心创建最小电路草稿
→ 插入必要/可选模块
→ 电路检查
→ 隔离测试
→ 查看发布差异
→ 发布不可变 Release
→ 可选固定到全局模式导航
→ 打开用户模式首页
→ 创建 Session Snapshot
→ 状态回流模式中心
```

发布前确认至少显示：

- 相对上一 Release 新增、移除、升级了哪些模块；
- 权限、MCP、Plugin 和凭据引用变化；
- 首页快捷任务或默认入口变化；
- 测试场景与结果；
- 新 Session 将采用新版本，现有 Session 不受影响。

发布成功后立即提供“打开模式首页”“固定到导航”“创建首次会话”。发布失败保留草稿和测试证据，进入“需要处理”，不能丢失插槽配置。

#### 5.5.9 全局模式导航与用户模式分割线

已发布模式可固定到左侧全局模式导航：

```text
固定产品模式
  Chat / Coding / Work / Assistant / 模式中心
────────────────────  用户模式分割线
用户固定模式
  安全审查 / 视频创作 / 更多模式
────────────────────
帮助 / 设置
```

- 固定产品模式与用户模式之间必须有稳定的弱分割线和辅助技术分组；不能只靠颜色区分。
- 没有固定用户模式时不显示空分区和孤立分割线；首个模式固定后出现。
- 分割线不进入键盘 Tab 顺序。用户模式不能覆盖固定产品模式，帮助和设置继续位于独立系统区。
- 可创建 N 个模式，但全局栏只显示当前高度可容纳的固定项；其余进入可搜索、可排序的“更多模式”。
- 固定只是导航偏好，不复制 Release、不改变权限。取消固定不删除模式、Session 或产物。
- 点击用户模式图标进入该模式的运行首页，不进入 Builder；编辑、依赖修复等操作深链回模式中心唯一 Builder。

#### 5.5.10 用户模式首页与 Session 边界

三类页面职责严格分离：

1. **模式中心**：创建、编辑、测试、发布、升级、复制、固定、停用、归档和依赖修复；
2. **用户模式首页**：选择项目、使用已发布入口、继续会话、查看产物和模式健康；
3. **Session 详情页**：具体对话、工具调用、权限审批、上下文、执行进度、产物、中断与恢复。

用户模式首页由平台受控组件构成，可配置欢迎语、推荐任务、快捷操作、默认输入、最近会话、最近产物和依赖健康；Profile 不得接管全局 Layout、Session identity、Permission 或注入未信任前端代码。

用户模式次级左栏统一为“项目 / 模式功能 / 会话”；右侧至少显示当前工作区、默认输入或快捷启动、继续工作、最近产物和模式健康。模式功能只暴露发布者明确配置的入口，不展示模块库全部命令。点击具体会话进入 canonical Session。

Custom Session 必须存在标准详情页，因为模式运行不是一次性按钮动作。它复用统一 Session 主链路，并额外显示模式名称、Release、Snapshot digest、实际加载模块、版本和健康。Session 中不能原地修改 Snapshot；“基于此会话改进模式”只深链到模式中心并创建/复用下一版草稿，经过重新检查、测试和发布后才影响新 Session。

#### 5.5.11 编辑、升级、发布、回滚与归档

所有模式编辑入口最终收敛到模式中心的唯一 Builder：

```text
模式中心“编辑下一版本” ─┐
用户模式首页“编辑模式” ─┤
全局模式菜单“编辑模式” ─┼→ 同一个下一版草稿 Builder
Chat 引用“评估升级” ────┤
Session“改进模式” ──────┘
```

- 已发布 Release 不可原地插拔；首次编辑从活动 Release 创建下一版草稿，已有草稿则继续同一草稿，避免多个含义不明的升级分支。
- Chat 模块产生新 revision 后，模式显示“比较/在下一版草稿中采用”，不自动替换。
- 发布通过原子操作切换 `activeRelease`；新 Session 使用新 Release，运行中和历史 Session 保持旧 Snapshot，全局固定关系不变。
- 回滚只把旧的不可变 Release 设为活动版本，不重写旧内容；若旧版本的外部执行依赖失效，仍按当前安全状态阻止新运行。
- 停用模式会阻止新 Session 并从导航取消固定，但保留版本、草稿、历史 Session 和产物；归档用于长期收口并可恢复。
- 删除默认是软删除/归档，不级联删除 Chat 模块、Session、Snapshot 和产物。彻底删除必须先证明没有发布引用、恢复和审计需求。
- 模式正文/Binding 在模式中心编辑；模块正文始终回到 Chat 编辑。Chat 保存新 revision 后返回 Builder，由用户比较并显式采用。

#### 5.5.12 路由、作用域与历史语义

目标路由语义可采用稳定 Profile ID：

```text
/mode/custom                         模式中心
/mode/custom/profile/{profileID}     用户模式首页
/server/{server}/session/{sessionID} canonical Session
```

具体路径需对齐现有 router 与 ADR，但必须满足：

- 模式改名不破坏收藏、固定入口和历史链接；
- Session 记录 Profile ID、Release revision 和 Composition Snapshot；
- Profile 更新不热替换运行中 Session 的 Prompt、Agent、工具、权限或 MCP；
- Profile 缺失、停用或依赖失效时提供可恢复错误页，不能静默回退默认 Custom 或 Coding；
- 个人模式与项目模式明确区分。个人模式运行时选择 Location，不能无提示引用某项目独有模块；项目模式不能离开所属项目后伪装成全局模式。
- 个人、项目、未来团队模式至少区分使用、编辑、发布和管理权限；能运行模式不等于能修改活动版本。

#### 5.5.13 红蓝对冲结论

- **继续使用当前“资产列表 + 使用方绑定 + 诊断”单页**：实现成本低，但首页、编辑和运行混杂，普通用户难以理解，长列表和误绑定无法根治，不采用。
- **Custom 与未来用户模式完全分开**：重复资产组合、发布、权限和会话模型，不采用。
- **每个用户模式成为动态 ProductMode**：扩散到 Schema、数据库、SDK、权限、Draft、路由和测试矩阵，删除/改名破坏历史语义，明确不采用。
- **固定 Custom 底座 + N 个用户 Profile + 强类型插槽 + 最小可运行发布**：普通用户通过插拔完成组合，专业用户可使用高级连接视图；协议仍复用资产、版本、权限和 Snapshot，是当前推荐方案。

#### 5.5.14 后续真实用户 E2E 门禁

实施后继续使用 Codex 内置浏览器验证：

- 无模式、无必要 Agent、只有最小 Agent、以及完整多模块四种创建路径；
- 最小电路不填 Workflow/Prompt/Skill/Command/MCP/Plugin 也能检查、隔离测试和发布；插入相关可选模块后才触发其条件门禁；
- 模块库按类型、来源、健康和引用筛选，单类加载失败隔离，243 条命令分页/虚拟化；
- 模块点击只预览，确认插入后才改变草稿；插槽兼容性、拔出、撤销和未保存保护；
- Chat 编辑模块生成新 revision，模式旧引用不变，比较并显式升级下一版草稿；
- Chat 资产详情正确显示模式、插槽、revision、Release 和 Session 反向引用；被引用模块归档不破坏历史；
- 电路检查、测试、发布按钮与诊断共享同一事实源，不再出现“诊断通过但无法启动”；
- 发布、固定、用户模式分割线、动态溢出、打开模式首页和创建首次 Session；
- 用户模式首页、模式中心和 canonical Session 之间的返回、深链和状态回流；
- 下一版编辑、发布差异、升级、回滚、停用、归档和恢复；
- 不同项目/模式之间无模块、草稿、会话、权限或 Snapshot 串线；
- Profile/模块缺失、版本漂移、MCP 断开、Plugin 隔离、凭据失效、权限拒绝、发布失败和恢复；
- 窄屏三列转抽屉、键盘、焦点、辅助技术分组及分割线行为。

在上述真实链路完成前，`/mode/custom` 保持 `PARTIAL`。当前 Builder 可达、资产可见或受控诊断测试不能外推为“模式创建、最小发布、版本管理和运行闭环已完成”。

### 5.6 跨模式首页公共契约（CONDITIONAL 审批）

> 审批结论：**CONDITIONAL / 有条件通过产品讨论稿，不批准直接按本文实施。** Chat、Work、Assistant、Custom 的目标方向已形成闭环，但 Coding 首页尚未专项定义，跨模式公共状态契约、作用域、路由恢复、异常矩阵和数据请求 owner 仍需收口。本文同时混合“当前事实、已确认需求、推荐方案和待裁决问题”，实施前必须拆为正式 PRD/ADR/计划并逐项标注状态。

#### 5.6.1 当前五类首页事实与目标边界

| 页面              | 当前真实结构                                       | 目标主职责                                            | 审批状态                                                       |
| ----------------- | -------------------------------------------------- | ----------------------------------------------------- | -------------------------------------------------------------- |
| `/` 全局首页      | 跨项目、跨模式会话聚合与筛选                       | 全局发现、筛选、继续会话和统一新建入口                | `PARTIAL`；不得承担某个模式的 Location/能力管理                |
| `/mode/chat`      | 左侧项目+功能，右侧七类资产表格；暂无左侧会话      | 资产创建/管理工作台 + 会话导航                        | `CONDITIONAL`；需补会话区、资产详情/引用/版本闭环              |
| `/mode/coding`    | 左侧多项目及项目级新建，右侧当前项目会话搜索与列表 | 代码项目与会话优先工作台                              | `PROPOSED`；见 §5.2                                            |
| `/mode/work`      | 左侧当前项目，右侧预设卡片目录                     | 继续工作优先的结构化任务工作台                        | `CONDITIONAL`；预设自建边界待 ADR 裁决                         |
| `/mode/assistant` | 左侧项目+知识入口，右侧固定提醒/知识库空态         | 个人/项目助手范围下的待处理、知识和会话工作台         | `CONDITIONAL`；个人物理目录与项目能力边界待设计                |
| `/mode/custom`    | 左侧混合资产长列表，右侧组合 Builder               | 模式中心：首页管理 N 个用户模式，Builder 负责插槽组合 | `CONDITIONAL`；Release/Revision Store/反向引用属于新增架构能力 |
| 用户模式首页      | 当前不存在                                         | 已发布用户模式的独立运行工作台                        | `PLANNED`；底层仍为 `mode=custom + profile/release`            |

横向审批确认：所有模式可以复用统一壳层和交互语法，但**不要求首页内容机械同构**。Chat 以资产为主、Coding 以代码会话为主、Work 以结构化工作为主、Assistant 以个人/项目助理为主、Custom 以模式治理为主。统一的是状态、导航、折叠、作用域、恢复、异常和无障碍契约，不是强制每页都显示相同三块卡片。

#### 5.6.2 跨模式统一左栏契约

各模式可按业务裁剪分组，但共享以下交互：

- 项目/范围区是 Location owner；能力、预设、模式等第二分组是领域导航；会话可在左栏或 Coding 的右侧主索引出现，但同一页面不得维护两套独立会话真源。
- 标题点击与箭头点击分离：箭头只展开/收起，标题可进入分组概览，具体条目执行选择或导航。
- 折叠状态采用统一持久化键。本文此前出现“用户+工作区”和 `server + workspace + mode` 两种口径，必须收敛为至少包含 `user/profile + server + Location identity + product surface` 的稳定 key；用户模式还需包含稳定 Profile ID，改名不得丢状态。
- 各分组统一标题高度、图标方向、命中区域、弱分隔、滚动边界、焦点样式、动效和 `aria-expanded`/`aria-controls`。折叠按钮、分割线和计数不能制造额外 Tab 停靠点。
- 长列表使用分页或虚拟化；标题和主操作在低高度下仍可达。分组收起后保留必要范围/异常摘要，但不能泄漏另一项目或个人范围的数据。
- 项目、能力和会话计数必须来自与右侧相同的 query/cache，不允许左栏为了计数重复请求完整数据。

#### 5.6.3 跨模式统一右侧联动与导航状态

每个模式首页都应遵循：

```text
右侧状态 = server/Location × 当前模式或用户 Profile × 当前领域选择 × 可选条目
```

- 切换 server、Location、个人/项目范围或用户模式时，先使旧数据失效，再显示新范围 loading；禁止旧项目内容闪现。
- 展开/收起左栏不改变右侧。只有选择项目、领域入口、筛选项或具体条目才改变右侧。
- 右侧顶部始终可辨认当前范围；项目场景显示项目、路径及真实可用的分支/worktree，个人场景显示个人目录，用户模式显示活动 Release。
- 右侧摘要卡、左侧列表、管理页和 Session 必须共享同一事实源。摘要只做入口，不能形成第二套可修改状态。
- 领域条目需要稳定可深链身份；URL 不写入澄清答案、Prompt、凭据和其他敏感正文。浏览器返回/前进应恢复范围、领域、筛选、选中条目和滚动，失效条目回到可解释的父级空态。
- 直接访问深链时必须先恢复对应 server/Location 和模式上下文；无权、缺失、停用或版本不兼容时显示可恢复错误，不静默切换项目或回退其他模式。

#### 5.6.4 新建入口与 Draft 原子继承

不同模式的主要动作可以使用业务化名称：Chat/Coding/Assistant 为“新建会话”，Work 为“新建工作”，模式中心为“创建模式”，用户模式为“开始任务”。但每类入口必须满足：

- 同一页面只存在一个视觉主操作；行内快捷入口为次级操作，且复用同一 resolver/事务。
- 创建时原子冻结 `server + Location/worktree + ProductMode + Profile/Release（如有）+ Agent + permission defaults`，不能先创建 Draft 再异步修补关键归属。
- 数据或能力尚未解析时禁用创建，并在按钮附近说明原因；失败保留用户输入，不产生幽灵 Session，不污染最近模式和会话计数。
- 首页筛选不等同于新建目标模式；继续遵循 §4.6 的 `homeSessionFilter`、`lastNewSessionMode`、`draft.mode` 分离。
- Custom/用户模式不得走普通空 Draft：必须从已验证 Release 原子创建 Session 与 Snapshot；Work 的预设澄清则在最终确认后才创建 Session。

#### 5.6.5 所有首页必须覆盖的状态矩阵

当前各专项对异常的描述不均衡。每个首页和每个独立数据区至少覆盖：

| 状态                           | 最低体验要求                                                       |
| ------------------------------ | ------------------------------------------------------------------ |
| 首次使用                       | 说明价值、数据保存位置和最小下一步，不直接展示无法行动的空仪表盘   |
| 无项目/未配置范围              | 提供统一目录选择或创建引导；不得发起依赖 Location 的请求           |
| Loading                        | 保持布局稳定，标识当前正在加载的范围；不显示上一范围数据           |
| Partial                        | 某类资源失败不清空其他成功数据，明确失败类别和局部重试             |
| Empty                          | 与请求失败区分，给出与当前模式相关的创建/导入入口                  |
| Error                          | 显示用户可理解的 cause、影响范围、重试/重新关联/返回操作           |
| Offline/重连                   | 已有只读摘要可保留但标记过期；写操作禁用，重连后做 freshness check |
| Path missing/permission denied | 不静默创建新目录；允许重新关联、切换范围或请求授权                 |
| Stale/version drift            | 保持当前稳定版本，显式比较并采用更新，不自动改写运行中对象         |
| Dirty/冲突                     | 离开前确认；CAS 冲突提供比较、重载或另存，不覆盖他人/另一窗口修改  |
| 大数据量                       | 分页/虚拟化、取消过期请求、稳定选择与滚动，不阻塞主线程            |
| 窄屏/缩放                      | 320px 等效宽度及 200% 缩放仍能到达范围、主操作和错误恢复           |

各区 Retry 必须只重试失败 query，不重复创建 Session、资产、提醒、预设或模式，也不能重复弹出权限申请。

#### 5.6.6 数据 owner、缓存与并发一致性

- 每个领域建立单一 read-model owner：项目、Session、Chat 资产、Work 预设、Assistant 数据、Custom 模式分别拥有可复用 query/cache。左栏计数、右侧摘要和管理列表基于同一缓存投影。
- 切换模式时应取消或忽略过期请求；隐藏 slot 不发送网络请求。不能重复当前 Chat 冷加载至少 14 次列表请求的问题。
- 写操作成功后通过同一 owner 失效或增量更新；失败回滚所有乐观 UI。多个窗口或文件 watcher 修改时执行 revision/CAS freshness check。
- 排序和时间统一使用稳定规则；同名项目、同名资产、同名模式和同名会话必须显示来源/路径/作用域，不能只靠名称识别。
- 计数应明确是否包含系统、项目、个人、无效、归档和隐藏项。Chat 当前左侧计数与右侧筛选结果若口径不同，会直接破坏用户信任。

#### 5.6.7 权限、隐私与破坏性操作

- 首页摘要不得展示 Prompt 正文、记忆正文、凭据、隐私附件或未授权跨 Location 内容；计数和标题也应遵循权限裁剪。
- 首页上的打开、重试和继续操作不能复用历史临时授权。实际执行继续经过 Permission；Snapshot/Release 只记录配置事实，不是永久授权。
- “关闭标签”“从列表移除”“归档”“停用”“删除磁盘内容”必须使用不同术语和确认级别。首页默认只提供非破坏性管理；物理删除进入明确详情流程。
- 个人助手目录、项目目录、用户模式和 Chat 模块跨范围引用必须显示来源与授权边界；切换范围后清除敏感详情和缓存投影。

#### 5.6.8 可访问性与可观测性公共门禁

- 所有图标按钮有可访问名称和 tooltip；状态不只靠颜色，计数/徽标有文本语义。
- 列表支持方向键或标准 Tab 模型，选中使用 `aria-current`/`aria-selected`，Tab 组件使用正确 tablist/tab/tabpanel 关系。
- Loading、局部失败、发布/保存成功和后台状态变化使用适当 live region，但避免高频状态刷屏。
- 键盘焦点在切换右侧、关闭详情、返回首页和错误恢复后移动到合理标题/触发点；虚拟化不能丢失焦点或读屏上下文。
- 埋点仅记录入口、状态、时长和错误分类，不采集 Prompt、记忆、知识正文、路径敏感片段或凭据。真实 E2E 的日志必须能关联 request/Session/Profile ID，但对用户内容脱敏。

### 5.7 首页阶段收口：决策台账与下一阶段边界

#### 5.7.1 已确认的产品方向（CONFIRMED）

- 全局首页保持跨项目、跨模式会话聚合，不变成某个模式首页；首页筛选和新建目标模式分离。

## 6. 全局底部模块专项（2026-09-10）

### 6.1 状态栏空态与数据源边界

- 非正式 Session 页面仍渲染会话型指标，出现 `localhost:4096 — — 0 —` 等低价值占位。首页、模式页和新建草稿页应只保留有意义的连接状态；无活动 Session 时隐藏会话指标、Context 和无数据占位。
- `createCurrentSessionSource()` 全局挂载且指标固定值直接写裸 `localStorage`；后续应复用统一 Persist/platform 机制，并验证多窗口、迁移和存储失败。
- 子代理统计通过 assistant message 的 agent/完成时间启发式推导，需与 delegation/background-job 的真实状态源核对，避免误计。

### 6.2 底部弹窗以点击位置为虚拟锚点

- 用户要求点击底部状态栏后，弹窗位置跟随本次鼠标点击位置，而不是固定在整条状态栏或页面预设位置。
- 鼠标点击时以落点创建虚拟锚点；弹窗打开后保持稳定，不随鼠标持续移动。键盘触发时回退到触发控件边界，保证可访问性。
- 必须做 viewport 碰撞检测并自动翻转/偏移，避免越界、遮挡状态栏或与 DebugBar、Help 重叠；窗口缩放后重新计算位置。
- 点击外部和 Escape 关闭后，焦点应回到原触发控件。需覆盖状态栏左、中、右不同落点及窄屏。

### 6.3 开发诊断与 Help 隔离

- DebugBar 与 HelpButton 同占右下区域，且分别使用 `DEV` 与 dev channel 两种门禁，显示策略不一致。
- Help 内容仍为 `Lorem ipsum`，关闭持久化被注释；该占位实现不得进入可交付构建。
- 开发诊断、用户帮助和产品状态栏应拆分层级，避免遮挡与误触。

## 9. 顶部 New session 的导航延迟：已定性为开发态过渡开销（2026-09-11）

> 本节记录一次独立现象的取证过程与结论。结论：**不是产品死锁，也不是 DESIGN.md 描述的路由冻结缺陷**；是开发态路由过渡在负载下的延迟，已用显式等待预算缓解。

### 9.1 现象与初始怀疑

- 用例：`packages/app/e2e/regression/global-shell.spec.ts:264` "the new-session button on a session route opens a draft tab that closes back to the session"。
- 失败形态：点击标题栏 "New session" 后 `toHaveURL(/\/new-session\?draftId=/)` 连续 10s（14 次轮询）未满足，URL 停在会话路由；同一用例在其他轮次通过，非稳定重现。
- 初始怀疑：与 `DESIGN.md` §Router Transitions And Resources 记载的"transition 游离 promise 导致导航静默冻结"同形。

### 9.2 取证（插桩：`newDraft` 调用点、guard 判定、URL 时间线，5 轮重复）

| 观察项                      | 结果                                                           |
| --------------------------- | -------------------------------------------------------------- |
| `tabs.newDraft` 是否被调用  | 每轮都调用（点击处理链完整，`server/directory/mode` 正常）     |
| `DirtyDraftGuard` 是否拦截  | 每轮都放行：`key=<session>`、`dirty: false`、未 preventDefault |
| URL 是否提交                | **5/5 全部提交**，无一轮冻结                                   |
| 提交延迟（点击 → URL 变化） | 1282ms / 1728ms / **4515ms** / 1285ms / 1690ms                 |

失败轮的高负载下超过了 10s 断言窗口，但机制与上面相同——过渡最终 resolve。

### 9.3 结论

- **导航不会永久冻结**：guard 不拦截、`newDraft` 正常、URL 必然提交；DESIGN.md 的"游离 promise"路径未被触发（全仓 `createResource(() => cond ? … : undefined)` 仅剩 app.tsx 启动健康检查，web 下立即 resolve；`whenActive` 站点是已知豁免）。
- **延迟来源是开发态路由过渡**：Vite 按需 transform + 挂载 new-session 子树，在本机负载下 1.3–4.5s，重负载时超过 10s。会话页到草稿页的过渡不是产品 SLA；生产构建的时序由 production smoke 与性能基准覆盖。

### 9.4 缓解

- 两个依赖"草稿路由已提交"的用例（new-session 打开、脏草稿关闭）把 URL 等待显式设为 30s，并注释说明这是开发态过渡预算、不是产品时限；禁止用缩短等待或断言标签代替 URL 断言（DESIGN.md 要求路由级导航必须断言 URL）。
- 若该延迟继续增长，应在生产构建里测量（`test:bench`），而不是收紧 e2e 窗口。

### 9.5 与关闭事务修复的关系

关闭事务（§8.2）与本次取证均未触及 transition 资源；两者独立。

## 12. Session 详情链路专项

### 12.1 Canonical Session route：E3 7/7，但发现四类路由错误

3. **P1 非 Git Location 的 Coding 边界不清**：Session 允许绑定非 Git 目录，右侧却以 Git 审查为主要入口。需要明确产品选择：支持普通目录并降级为“文件”，或在创建 Coding Session 时明确提示 Git 能力不可用；不得把“创建 Git 仓库”作为默认无解释修复。
4. **P2 详情页模式识别依赖全局导航**：虽然全局“编程”图标被选中，但正文没有 Coding 专属身份和能力摘要，用户切换多个不同模式 Session 时容易误判当前执行边界。
5. **P2 加载反馈过粗**：刷新先恢复外壳和项目栏，再长时间显示统一“加载中”，随后消息与指标分批补齐；缺少 Session 元数据、消息、右栏能力的独立骨架、失败归因和重试入口。
6. **P2 操作菜单边界过宽**：重命名、分享、定时任务、我的智能体、归档、删除集中在同一菜单，但未在入口层表达哪些是当前模式能力、哪些会跨 Session/资产域、哪些属于破坏性操作。

**UNVERIFIED，不能据此宣称 Coding 详情页闭环：**

- Composer 到 durable admission、SSE 流式 parts、完成/失败、steer/queue/stop 与重试；
- 模型、Agent、推理强度与权限切换是否写入正确 Session 边界；
- 真实文件读写、Diff/Review、Git 仓库、Terminal/PTY 生命周期；
- 子会话/委派、并发 Tab、断网重连、后端重启恢复、归档和返回首页状态恢复；
- 非 Git、脏工作树、超长历史、工具审批中、失败或中断中的完整状态矩阵。

首轮结论：canonical 路由、历史读取与刷新恢复可用，但详情页尚未达到 Coding 工作闭环。下一轮必须使用专用可回收测试 Session 和可控 Git fixture，避免在现有真实会话或用户目录中执行破坏性验证。

### 12.6.1 Coding Session 真实开发者主任务链与区域职责（2026-09-12）

本轮角色是“接手一个已有仓库中的真实开发任务，并需要安全完成修改、验证和交付的开发者”。Codex 内置浏览器控制当前返回 `CUA_REPL_ENABLED_SURFACES is required`，且 `4444/4096` 均无监听；因此本节将既有 §12.1-§12.6 E3/E4 事实与当前代码结构组合为产品流程审查，不新增 E4 通过声明。

**详情页区域先收敛为五个职责区：**

```text
次级左栏 S           中央会话区 M                   右侧工作区
项目/Worktree/会话    消息时间线 + Composer          A：Review/文件/Context
                                                    B：Changes/All 文件树
底部 T：显式 Terminal/PTY（可开关，不替代工具调用记录）
```

- `S` 负责导航和范围识别。Coding 详情页保留项目树是合理的，因为项目、Worktree 和 Session 是编码任务的核心边界；但默认只展开当前项目/Worktree，其他项目折叠。项目标题只展开/收起，项目行或 Session 行才执行导航。
- `M` 是任务控制面：用户需求、计划、流式输出、工具调用、权限审批、Todo/进度、错误恢复和 Composer。切换 Review、文件、Context 或 Terminal 都不能替换 M。
- `A` 是检查与证据面：Review 总览、具体 Diff、文件内容、Context/Token 诊断。一个时刻只显示一个主检查对象，并具有清楚的标题、路径和状态。
- `B` 是导航树：`Changes` 只显示当前审查基线下的变更，`All` 显示当前 Location 文件；它不能单独承担内容详情。
- `T` 是用户主动控制的交互式终端。Agent 工具调用仍留在 M 的时间线中；不能把不可审计的 Terminal 输出冒充 Agent 工具证据，也不能因切换 Session 隐式销毁仍在运行的 PTY。

#### 真实开发者完整主链

1. **从 Coding 首页进入 Session。** 点击会话整行进入 canonical Session，标题区必须先确认模式、项目、Location/Worktree、分支或“非 Git”、Agent、模型和当前权限。M 加载历史和草稿，A/B/T 按该 Session/Location 恢复。元数据未解析前显示中性骨架，不能先挂载其他模式或错误目录。
2. **理解并确认任务。** 用户阅读最近消息、Todo 和当前工作树状态，在 Composer 补充验收标准。若 Session 已有未完成运行、待审批或失败恢复点，页面优先显示 `继续 / 停止 / 查看问题`，不能同时让用户误以为可以无冲突启动第二个执行。
3. **提交请求并观察执行。** Enter 形成 durable input，M 乐观显示但必须区分 `正在提交 / 已接收 / 正在执行 / 等待权限 / 失败 / 完成`。运行中新的输入明确为 steer 或 queue；Stop 只中断当前执行，不删除已落盘文件、历史消息或排队输入。HTTP 成功不等于任务完成。
4. **处理工具和权限。** 每次文件写入、shell、网络或高风险工具审批显示动作、作用域、理由和影响范围。`允许一次 / 始终允许 / 拒绝`必须说明作用域；临时全权显示有效期、撤销入口和当前是否生效。拒绝后 Agent 获得结构化结果并可提出替代方案，Session 不能卡在永久 busy。
5. **变更出现并联动右侧。** 新增/修改/删除文件后，B 的 `Changes`计数和树更新；点击变更文件在 A 打开对应 Diff 并定位，M 保持。点击普通文件时 A 打开文件、B 切到或保持 `All`并定位。自动联动不能抢走正在输入的 Composer 焦点。
6. **逐文件审查并反馈。** Review A 显示总览、文件状态、增删行和审查基线；用户逐个查看 Diff、添加行级评论或将选中代码加入 Context。评论必须能转成一条可追踪的后续请求，并具有 `待处理 → 已回应 → 已解决/重开`状态；仅把文字放入 Composer 而没有来源路径/行范围不算闭环。
7. **运行验证。** 用户可以要求 Agent 运行测试，也可以显式打开 T 手工运行。验证记录至少保存命令、目录、开始/结束时间、exit code 和对应变更基线；长任务可取消，终端断线可重连或明确显示进程已丢失。一次绿色测试只证明对应 revision/baseline，后续文件变化后应标记“验证结果可能过期”。
8. **失败后迭代。** 编译、测试、权限、工具或模型失败均回到 M 的可操作状态；保留失败输出和 Composer 草稿，提供重试、修改请求、切换模型/权限或停止。重试必须区分“重试相同 provider turn”和“创建新的修复请求”，避免重复副作用。
9. **完成前总审查。** 页面汇总变更文件、未解决评论、未完成 Todo、验证结果、未跟踪/未保存状态和权限提升状态。用户可以返回任一 Diff/消息/终端证据继续修复。若工作树存在 Session 开始前的用户变更，必须与本 Session 产生的变更区分，不能声称全部由 Agent 完成。
10. **交付。** Coding Session 的最小完成定义是：需求结果摘要、实际变更清单、验证证据、已知风险和下一步均可读取。Session 完成不应自动 commit/push；只有产品提供明确 Git 工作流时，才由用户显式选择 stage/commit/PR，并准确展示纳入范围。没有内建 Git 交付能力时，提供可复制的交接摘要和“在外部 Git 工具继续”，不能用“完成”暗示代码已提交。
11. **离开、切换和恢复。** 切换项目/Worktree/Session 只切视图，不隐式 stop、归档或迁移当前 Session。每个 Session 恢复自己的 M 草稿、A 活动 Tab、B 模式/宽度/展开节点和 T；Terminal 按 `server + Location`共享时必须明确标识，不得显示成 Session 私有。刷新或后端重启后重新验证 Session、Location、文件和运行状态，失效对象回退概览并说明原因。
12. **撤销和事故恢复。** Revert/undo 先预览受影响消息、文件和是否覆盖用户后续修改；存在工作树冲突时停止并要求人工裁决。删除/归档 Session 不删除项目文件或 Git 历史；Reset/Delete Worktree 必须独立高风险确认、先检查脏文件和运行中的 Terminal/Session，并提供可恢复边界。

#### 左侧标题、列表与 A/B/T 联动契约

| S 或工作区动作         | M                               | A                                 | B                                  | T                            |
| ---------------------- | ------------------------------- | --------------------------------- | ---------------------------------- | ---------------------------- |
| 项目标题展开/收起      | 保持                            | 保持                              | 保持                               | 保持运行                     |
| 当前项目/Worktree 概览 | 保持当前 Session                | 显示只读范围、Git、权限和运行状态 | 默认保持；显式“浏览文件”后显示 All | 保持                         |
| 当前 Session 行        | 保持/幂等                       | 恢复该 Session 最近 A             | 恢复该 Session/Location B          | 恢复并标明共享范围           |

| Changes 文件           | 保持                            | 打开 Diff/Review 并定位           | 显示 Changes 并选中                | 保持                         |

统一优先级是：`用户显式操作 > 当前任务产生的联动 > 恢复状态 > 默认 preset`。例如文件变更事件可以更新 Changes 计数，但不能在用户阅读 Context 时强制切回 Review；只有用户点击消息中的具体文件、Diff 或“查看变更”才打开 A/B。

#### 非 Git Location 的产品边界

Coding 必须支持普通目录的降级路径，而不是把“创建 Git 仓库”作为唯一答案：

- 普通目录仍可使用消息、文件、工具、Terminal 和基于 Session Snapshot 的变更查看；Git 分支、stage、commit、基于分支的 Diff/PR 明确不可用。
- 用户可主动初始化 Git，但操作前说明会在物理目录写入 `.git`、可能改变后续 Diff 语义，并要求明确确认。
- 如果某项 Coding 能力确实要求 Git，应在入口和动作附近写明原因，并提供“继续使用普通目录”而非死路。

#### 第一轮闭环判定

主链从进入 Session、请求执行、权限、文件变化、Review、验证、迭代到交付与恢复在产品逻辑上可以闭合；但当前实现和证据仍为 `PARTIAL / PRODUCT CONTRACT PROPOSED`。已有 E3 仅分别证明 Composer 提交前半链、mock Files 和 mock Terminal；既有 E4 只证明真实 Session 的读取、Context 和刷新恢复。以下缺口在进入多角色裁决前必须保留为开放项：

1. Coding 标题区的范围/权限/分支身份和分阶段错误恢复；
2. Session 运行状态、steer/queue/stop 与 durable execution 的真实闭环；
3. Review 评论到后续修复再到 resolved 的追踪模型；
4. 变更归属、审查 baseline 与验证结果过期机制；
5. Terminal 进程在切换、断线、刷新和 Location 删除时的生命周期；
6. 非 Git 目录的 Snapshot Diff 降级能力；
7. 完成定义、交接摘要以及 Git commit/PR 的明确产品边界；
8. Revert 与用户既有/并发修改之间的冲突保护。

下一轮应按首次开发者、日常实现者、Reviewer、调试/Terminal 用户、多 Worktree 用户和受限/故障用户进行红蓝对冲，再形成 Coding 详情页最终功能矩阵和 E4 验收路径。

#### 12.7.4 Chat 会话详情页次级左栏与主区 A/B 联动契约（2026-09-12）

**术语先收敛：** 会话详情页至少有三个不同职责区，不能都叫“主区域”。

```text
次级左栏 S         中央会话区 M                    右侧工作区
项目/会话资产/会话  消息时间线 + Composer          A：上下文详情/检查器   B：文件树
```

- `M` 是 Session 的持续工作面，除切换到另一 Session 或离开详情页外不得被左栏普通选择隐藏或替换。
- `A` 是与当前 Session/当前选择联动的检查器，可显示资产候选、已用资产、Context、产物、提醒/知识实体、Workflow 运行、Review 或具体文件。
- `B` 是文件导航区，只在文件、Diff、产物落盘或“定位到文件”语义成立时显示；不能因点击任意业务分类就机械出现。
- A/B 可以独立开关，但必须由一个声明式 `selection → panel preset` 映射决定，不能让左栏、右栏 Tab 和全局 store 各自保存一份互相漂移的选择。

**CURRENT 实现事实与缺口：**

- Chat Session 次级左栏已经按“项目 / 功能 / 会话”三段渲染，三个段落可独立折叠，折叠状态按 server + workspace 持久化；功能段仍展示完整七类资产树。
- 点击七类功能项只更新全局 `ChatFeatureProvider.selected`；右侧 `ChatRightPanel` 的 A 区仍由 Preview/Context/file Tab 决定，两者没有共同选择真源。因此在 Session 中点击 Prompt、Skill、MCP 等可能只改变一个隐藏/无反馈状态，并不会打开对应详情。
- `SessionRightPanel` 已统一 A/B 壳：A 是各模式注入的内容，B 是共享 `SessionFileTree`。但当前 A 的 opened 状态、B 的 file-tree visibility 与左栏分类没有形成业务映射。
- Assistant 已有较合理的先例：左栏 Reminder/Memory/KB 实体选择会通过 `openEntityPanel` 打开右侧对应 Tab；Work 的 trade/taskSet/agent Tab 当前只替换左栏内容，右侧 Artifact/Context 不随之联动。应抽象统一选择契约，而不是继续为每个模式写不同隐式规则。

**是否保留完整资产功能树：保留“会话资产投影”，不保留第二套完整资产库。**

Chat Session 次级左栏的资产段建议从首页的全量七类库改名为**会话资产**，默认只显示本 Session 有关系的内容：

```text
会话资产                              [折叠]
  已使用  4
    Agent 1 · Prompt 1 · Skill 1 · MCP 1
  新提案  1
  有更新  2

- 七类 kind 仍作为二级筛选存在，但无关联的分类默认不占空间；用户展开“全部分类”后才显示零计数分类。
- “已使用”必须来自结构化 Session asset reference/Snapshot，不得从消息正文猜测；每项显示来源 Location、冻结 revision、最新 revision 和状态。
- “新提案”连接右侧 Preview/Apply；“有更新”连接版本比较；“问题”连接缺失、失效、权限、凭据或解析诊断。

**标题、列表项和右侧区域的交互规则：**

1. **段落标题点击只展开/收起左栏内容，不改变 M、A、B。** 标题按钮使用 `aria-expanded/aria-controls`；折叠不是选择，不能清空当前 A，也不能停止运行中的 Session。
2. **段落总览使用独立“查看全部/概览”入口。** 不把标题同时做折叠和导航，避免一次点击有两种结果。
3. **点击具体业务项才改变 A。** 选择必须有左栏选中态、A 区标题/面包屑和 URL/Session view state；再次点击当前项保持幂等，不反复开 Tab。
4. **点击会话项改变 M。** 进入对应 canonical Session，M 切换消息与 Composer；A/B 恢复该 Session 上次有效状态，不能继承上一 Session 的敏感资产详情或文件。
5. **项目/Location 在既有 Session 中是身份而非可变筛选。** 点击当前项目可在 A 显示只读 Location/分支/权限概览；切换项目必须进入该项目首页或新建 Session，不能把当前 Session 原地迁移到另一物理目录。
6. **折叠左栏不影响运行。** 左栏整个关闭、某段折叠或滚动，都不能终止流式输出、丢 Composer 草稿、关闭 A/B 或重置 Context。
7. **窄屏降级为抽屉。** 选择业务项后可自动收起左栏抽屉以腾出空间，但这只是响应式壳行为，不等于隐藏 M；A/B 以单面板 Tab 形式显示。

- 允许自动**打开 A**：用户点击有明确详情语义的业务项时；A 显示对应 Inspector。
- 允许自动**隐藏 B**：从文件语义切换到纯资产/Context/权限语义时，减少无关噪声；B 的宽度和展开状态仍按 Session 记忆，回到文件项时恢复。

  | { kind: "file"; path; review?: boolean }
  | { kind: "artifact"; artifactID }

PanelPreset = { main: "session"; a: InspectorKind | "closed"; b: "project" | "artifact" | "closed" }
```

该状态按 server + Location + Session 持久化；左栏只发出 selection，A/B shell 只消费映射结果。数据失效时回退到 Session overview/模式默认 Inspector，并显示原因，不能渲染上一项目的陈旧内容。

**闭环验收路径：**

```text
Session 加载并投影已用资产
→ 左栏“会话资产”显示真实计数
→ 选择某资产，A 显示冻结 revision 与健康
→ 打开完整资产详情/比较新版
→ 显式升级或保持冻结
→ 返回 Session，引用状态即时回流
→ 刷新/切换会话恢复各自 A/B 状态
→ 折叠/关闭左栏不影响消息流和草稿
```

必须补 E2E：标题折叠不改变 A/B、七类选择打开正确 Inspector、文件选择自动打开 B、非文件选择关闭但可恢复 B、Session 切换不串状态、Dirty/Busy guard、窄屏抽屉、刷新恢复、资产升级后反向引用更新。当前实现尚未具备上述共同选择真源，因此本节为 `CONFIRMED/PROPOSED` 契约，不是 `IMPLEMENTED`。

### 12.7.5 Chat Session 真实用户任务链复盘与闭环补充（2026-09-12）

本轮以“我正在一个 Chat Session 中继续工作，已经使用若干资产，同时收到一个新资产提案”为真实任务，不把单次点击成功等同于业务完成。受控内置浏览器当时不可操作且 `4444/4096` 均未监听，因此以下是基于当前实现事实、已有 E3 回归和 §12.7.3-§12.7.4 契约完成的产品任务链审查，不冒充 E4 实机通过。

**完整任务链：**

1. **从 Chat 首页进入既有会话。** 用户点击会话整行后进入 canonical Session；M 立即显示该 Session 的消息与 Composer。首次进入时 A 默认显示 Session 概览或关闭、B 默认关闭；再次进入时按 Session 恢复上次有效状态。加载、空数据、离线和恢复失败都必须在对应区域给出可重试状态，不能用上一 Session 的缓存假装成功。
2. **确认会话边界。** 左栏项目段只显示当前 Location/项目身份；点击项目概览在 A 查看路径、分支和权限。不能在既有 Session 中通过项目列表原地替换工作目录。折叠项目、会话资产或会话段只改变左栏高度，不改变 M/A/B、Composer 草稿或流式执行。
3. **查看本会话已使用资产。** “会话资产 → 已使用”必须由结构化引用/Snapshot 生成。点击资产后 A 显示类型、来源、冻结 revision、最新 revision、健康、首次/最近使用位置和消费者；M 保持。若引用已失效，A 显示缺失、归档、权限或解析原因及修复入口，不能回退成无反馈空白。
4. **处理可用更新。** 用户从“有更新”进入 revision Diff，可明确选择“保持当前冻结版本”或“升级”。保持冻结不改变任何运行；升级只影响确认后的未来使用，历史消息和历史工具执行继续引用原 revision。Session 正在生成时不得把新 revision 注入正在进行的 provider turn；应显示“将在下一安全边界生效”，失败则原绑定保持不变。
5. **处理对话中新提案。** 点击“新提案”后 A 显示候选内容、类型专属校验、保存 Location/路径和冲突策略。`应用`仅表示生成并读回一个项目资产 revision，不等于已测试、已绑定或已投入当前 Session。成功后必须给出明确下一步：`在隔离环境测试`、`用于当前会话`、`打开资产详情`；“用于当前会话”再次确认 revision 和生效边界。应用失败保留候选与用户输入，路径冲突进入比较/另存/覆盖 CAS 流程。
6. **在当前会话使用资产。** 绑定操作写入结构化 Session asset reference；若 Session 空闲，从下一次提交开始生效；若正在运行，则在下一安全 provider-turn 边界生效并明确提示。每次实际使用记录当时 revision，不能靠资产当前文件内容反推历史。绑定成功后左栏计数、A 的消费者信息和 Chat 资产详情反向引用同步更新；失败时不出现“已使用”假状态。
7. **查看文件、Diff 或落盘产物。** 点击文件语义项后 M 保持，A 显示内容/Diff/产物，B 自动展示对应项目或产物树并定位。切回资产、Context 或权限项时可以自动隐藏 B，但保留 B 的宽度、展开节点和滚动状态；用户手动关闭 B 的选择优先于当前项的默认 preset，直到再次点击“定位文件”或另一个文件项。
8. **关闭 A 或切换左栏项。** 用户手动关闭 A 时清除当前 Inspector 可见选择并回到 Session overview/closed，不能留下“左栏仍选中但右侧无内容”的假选中态。A 中有编辑草稿、Apply、权限确认或运行中 Workflow 时，切换先触发 Dirty/Busy guard；保存、放弃或留在当前项后才改变 selection。
9. **切换到另一会话。** 原 Session 的流式任务继续由其运行状态管理，切换页面不能隐式中断；会话列表显示运行中/等待授权/失败摘要。新 Session 恢复自己的 M、Composer 草稿和 A/B view state，不继承原 Session 的资产、文件、权限详情。返回时原 Session 状态仍可恢复。
10. **往返完整资产库。** “查看完整资产库”进入 Chat 首页并携带 Location、资产 kind、asset ID/revision 和 `returnTo`；返回后恢复原 Session、左栏滚动和 Inspector。普通 Inspector 选择使用可恢复 view state，不为每一次折叠制造浏览器历史；跨页面、跨 Session 和进入完整资产库才进入正式导航历史。
11. **刷新、数据变化和并发。** 刷新后恢复的 selection 必须重新验证 server、Location、Session、asset ID 和 revision；失效时回退概览并说明原因。资产升级、归档、权限和健康变化通过统一数据源回流；并发升级采用 expected revision/CAS，冲突时重新比较，不能覆盖另一窗口的新版本。
12. **空态、窄屏和键盘路径。** 无关联资产时显示“当前会话尚未使用资产”和“前往资产库”，而不是七个空分类。窄屏中 M 始终是基础工作面，S/A/B 作为可切换抽屉；选择后可收起 S，但不能丢焦点、草稿或运行状态。标题折叠、列表选择、关闭面板和 Dirty guard 均需具备键盘操作、可见焦点及正确 ARIA 状态。

**复盘后收敛的关键规则：**

- `应用资产 ≠ 测试资产 ≠ 绑定资产 ≠ 在一次运行中实际使用资产`；四个状态必须分别持久化和展示。
- revision 升级遵循“历史冻结、未来生效、运行中等待安全边界”，否则无法解释重放、审计和失败恢复。
- `PanelPreset` 是业务选择的默认布局，不覆盖用户随后主动关闭 B 的决定；新的文件/定位动作才重新打开 B。
- 右侧关闭动作必须同步清理或降级 selection，避免左栏选中态与实际可见内容冲突。
- Session 切换只切视图，不隐式 interrupt；运行状态、草稿和 A/B 必须按 Session 隔离。
- 完整资产库往返需要 `returnTo` 和可验证的 deep-link 状态，不能依赖全局 Chat 分类碰巧仍在内存中。

**闭环判定：** 补入以上规则后，产品层从发现、应用、测试、绑定、运行、升级、回流、异常恢复到归档引用门禁已经形成逻辑闭环；但工程验收仍为 `NOT IMPLEMENTED / E4 NOT VERIFIED`。当前已确认代码缺少统一 `SessionDetailSelection`、结构化 Session asset reference/revision、资产 Inspector、Apply 后续状态持久化、A/B 共同映射和 Dirty/Busy guard。只有这些实现完成，并通过 §12.7.4 所列 E2E 以及本节 12 步真实浏览器回归后，才可把 Chat Session 详情页标为端到端闭环。

### 12.7.6 Chat Session 多角色红蓝对冲与功能闭环裁决（2026-09-12）

本轮不再只用“熟悉资产和 revision 的高级用户”验证，而是让六类用户完成各自真实目标。红方负责指出用户会卡住、误解或造成状态/权限事故的路径；蓝方只接受可落地、可恢复、可测试的收敛方案。Codex 内置浏览器控制仍返回 `CUA_REPL_ENABLED_SURFACES is required`，且 `4444/4096` 无监听，因此本节是角色化任务模型审查，不计作 E4 实机证据。

#### 角色 1：首次使用者——“我只想让当前会话更好用”

**任务路径：** 进入空 Session → 不知道什么是会话资产 → 寻找可用能力 → 选择一个 Prompt/Skill → 继续对话。

- **红方发现：** 只有“已使用 / 新提案 / 有更新 / 问题”无法覆盖“尚未使用、现在想添加”的首次任务；“查看完整资产库”让用户离开正在进行的会话，成本过高。直接暴露 SHA-256 revision、Snapshot、绑定和 provider-turn 等术语也会阻断新手。
- **蓝方裁决：** “会话资产”段必须增加主入口 `＋使用资产`。点击后在 A 打开 Session-scoped asset picker，默认按当前 Location、兼容性和最近使用筛选；`查看完整资产库`保留给创建、导入和批量治理。列表主文案使用“当前版本 / 有更新 / 下次消息生效”，精确 revision、来源路径和安全边界放入“技术详情”。
- **闭环结果：** 选择后必须返回会话上下文并显示下一步，而不是停在资产详情。若当前 Session 无资产，空态应为“尚未使用资产”+ `使用资产`；若没有任何可用资产，再引导到资产库创建/导入。

#### 角色 2：普通会话用户——“使用资产”并不是一种统一动作

**任务路径：** 在同一 Session 中分别选择 Prompt、Skill、MCP、Command、Agent、Workflow 和 Plugin。

- **红方发现：** 把七类资产全部抽象成“绑定到当前会话”是伪闭环。Prompt/Command 通常是一次性输入或调用，Agent 是切换执行身份，Workflow 是启动一次运行，MCP/Skill/Plugin 才更接近启用能力；这些动作的生效、撤销和审计完全不同。
- **蓝方裁决：** A 区必须按 kind 展示类型专属主动作，不能使用一个万能按钮：

| 类型     | 会话内主动作                          | 成功后的可见结果                        | 撤销/结束                       |
| -------- | ------------------------------------- | --------------------------------------- | ------------------------------- |
| Prompt   | 填写变量 → 插入草稿；可选“固定到会话” | Composer 出现可编辑草稿；固定时生成引用 | 删除草稿或取消固定              |
| Command  | 填参数 → 预览 → 插入/显式执行         | 草稿或新的受审计执行记录                | 执行前取消；执行后只可停止/重试 |
| Skill    | 为会话启用                            | “已启用”及适用触发方式                  | 禁用，未来 turn 生效            |
| MCP      | 诊断并授权后启用                      | 连接、工具范围和权限状态                | 断开/禁用并撤销后续可用性       |
| Agent    | 切换/委派给该 Agent                   | 当前 Agent 或 handoff 状态改变          | 切回/结束委派                   |
| Workflow | 填写输入并启动一次 Run                | 独立 run、步骤和产物状态                | 取消/恢复/重试 run，不称为解绑  |
| Plugin   | 检查来源和权限后为项目/Session 启用   | hooks/tools/commands 的启用范围         | 禁用；保留历史执行证据          |

- **闭环结果：** 左栏“已使用”必须区分 `已固定`、`已启用`、`当前 Agent`、`运行中/已完成`和`曾使用`，不能把一次 Prompt 插入永久显示为仍在启用。

#### 角色 3：资产作者——“应用成功”以后还要完成交付

**任务路径：** 对话生成提案 → 应用到项目 → 编辑 → 类型校验/试用 → 发布 revision → 被 Session/模式引用 → 升级或归档。

- **红方发现：** 当前“应用”只写文件并显示模块级布尔状态；没有持久化 applied revision、来源 Session、测试记录和下一动作。被引用资产若简单标成“不可编辑”，作者也无法发布修复；若允许原地编辑，又会破坏消费者冻结版本。
- **蓝方裁决：** `应用`只创建/更新 Draft revision；成功页的主动作按风险显示 `继续验证`，次动作是 `用于当前会话`和`打开资产详情`。已发布或已引用 revision 永久不可原地改写，但资产并非永久不可编辑：`编辑`必须从该 revision 派生新 Draft。发布前执行类型专属最低门禁，测试失败只阻止新 revision 发布，不影响现有 Published revision。
- **生命周期：** `Proposal → Draft → Validated → Published → Deprecated → Archived`；Draft 可删除，Published revision 不可删除。归档后禁止新消费者引用，但现有消费者继续读取冻结快照并收到迁移提示；只有具备耐久 revision/snapshot store 时才允许带引用归档，否则必须阻断归档。
- **闭环结果：** 资产详情反向列出引用它的 Session、用户模式及其冻结 revision；编辑生成新版后消费者只看到“有更新”，不会自动升级。

#### 角色 4：资产消费者——“升级不能改变已经发生的历史”

**任务路径：** 查看当前资产 → 收到更新 → 比较 → 保持、升级或回滚 → 继续发送消息。

- **红方发现：** 单一“升级”按钮没有说明影响范围；如果 Session 正在流式运行时替换能力，会出现同一个 provider turn 前后配置不一致。若失败后仍更新左栏计数，会产生假绑定。
- **蓝方裁决：** 比较页必须明确“当前冻结版本”“目标版本”“影响未来哪些动作”。`保持当前版本`是正式决策且可稍后处理；`升级`采用 expected revision/CAS，只改变未来使用。运行中升级排队到下一安全 provider-turn 边界，当前运行、历史消息和历史工具调用继续引用原 revision。升级失败保持原绑定；成功后提供 `撤回到上一版本`，回滚同样生成一次可审计引用变更。
- **闭环结果：** Session 左栏、A Inspector、Chat 资产详情反向引用和下一次实际运行记录必须由同一个引用数据源更新；四处任一不一致都判定失败。

#### 角色 5：多项目高级用户——“不能串目录、串资产或串右栏状态”

**任务路径：** 同时打开项目 A/B 的 Session → 在 A 查看资产和文件 → 切到 B → 进入完整资产库 → 返回 A。

- **红方发现：** 全局 `ChatFeatureProvider.selected` 无法表达 Session、Location 和 revision，容易让 B Session 看到 A 的选中项；跨项目资产若只按名称匹配，还会绑定同名错误资产。仅靠内存恢复 `returnTo`，刷新后会丢失来源页面。
- **蓝方裁决：** selection 和 A/B view state 按 `server + Location + Session` 隔离；引用身份至少包含 `assetID + origin + revision`，名称只用于显示。项目资产默认只能被同 Location 使用；跨项目使用必须显式“复制/导入到当前项目”，系统/用户全局资产则显示其作用域。完整资产库 deep link 必须携带并验证 `returnTo + Location + assetID + revision`；发现目标已失效时回到对应 Session 概览并说明原因，绝不展示另一项目缓存。
- **闭环结果：** Session 切换不隐式 interrupt，M/草稿/A/B/文件树分别恢复；顶部 Tab 关闭只关闭视图，不删除 Session 或资产引用。

#### 角色 6：受限、异常和辅助技术用户——“失败以后仍然能继续”

**任务路径：** 只读系统资产、MCP 无凭据、权限被拒、离线、CAS 冲突、资产失效、窄屏和纯键盘操作。

- **红方发现：** 禁用按钮但不解释原因不构成恢复路径；MCP/Plugin 若显示原始 env 会泄漏凭据；A 有未保存内容时自动切换会丢数据；窄屏自动收栏可能把焦点丢到不可见区域。
- **蓝方裁决：** 每个不可用动作同时显示原因和可执行下一步：请求权限、配置凭据、复制为项目资产、重连、重新比较或保持冻结。凭据只显示键名和配置状态，绝不回显值。离线时允许查看已缓存且明确标记的只读快照，禁用 Apply/升级并保留输入；恢复后重新校验 expected revision。Dirty/Busy guard 提供“保存并切换 / 放弃并切换 / 留在当前项”，Apply 和权限确认期间不能销毁面板。标题和列表项分离，支持键盘、可见焦点、`aria-expanded/controls/current`；抽屉关闭后焦点返回触发项，M 和 Composer 始终可达。
- **闭环结果：** 所有错误都必须满足“错误归因明确、原输入保留、当前已发布/已绑定状态不变、存在重试或退出路径”四项，缺一项即不闭环。

#### 红蓝对冲后的统一信息架构

```text
会话资产
  ＋ 使用资产                  → A：Session asset picker
  已固定 / 已启用 / 当前 Agent → A：类型专属 Inspector
  运行中 / 已完成              → A：Workflow/工具运行详情
  新提案                       → A：Preview → Apply Draft → 验证/使用
  有更新                       → A：revision Diff → 保持/升级/回滚
  问题                         → A：诊断和恢复
  查看完整资产库 ↗             → Chat 首页资产库，携带 returnTo
```

A/B 自动联动规则保持 §12.7.4，但增加两个优先级：`显式用户动作 > 当前项默认 PanelPreset > 恢复的上次状态`；新的文件/定位动作可打开 B，用户随后手动关闭 B 后，普通数据刷新不得再次打开。关闭 A 时 selection 降级为 Session overview/closed；不能保留假选中态。

#### 最小发布/使用门禁按风险分层

- **Prompt/Command：** 结构解析、必填变量/参数和展开预览是最低门禁；执行仍需用户显式确认。
- **Skill/Agent：** Schema、依赖、模型/工具可用性和权限摘要是最低门禁。
- **MCP：** 配置 Schema、凭据键状态、连接/工具发现和权限确认是最低门禁。
- **Workflow：** DAG、必需输入、步骤依赖、重试/取消策略和权限总和是最低门禁；不要求填满所有可选插槽。
- **Plugin：** 来源/版本、manifest、hooks/tools、权限和信任检查是最低门禁。

这保留“最小范围即可发布”的原则，但“最小”由类型风险决定，不等于所有插槽必填，也不等于任何候选都能无验证发布。

#### 多角色闭环结论与实施门禁

角色对冲发现并修复了三处原产品模型缺口：缺少 Session 内 `使用资产`入口、七类资产被错误统一为“绑定”、已引用资产的“不可编辑”缺少“派生新 revision”出口。补入本节裁决后，六类用户在产品逻辑上均有入口、成功反馈、失败恢复和返回路径，判定为 `PRODUCT FLOW CLOSED`。

1. 建立耐久 Asset revision、Session asset reference/actual-use 和反向引用模型；

1. canonical Session 冷启动先将 `Session.directory/projectID → realpath/stable Location identity` 归一化，再产生 `resolved | aliased | relocated | missing | inaccessible` 五类显式结果；主消息、Review、Files、Terminal、权限和新建动作必须共同消费这个 resolved Location。
2. `aliased` 时保留历史原路径并显示当前规范路径；`missing/inaccessible` 时冻结所有 Location-scoped 写操作与 Review/Files/Terminal 数据加载，展示原路径、失效原因和“重新关联 / 迁移 / 只读查看历史 / 返回 Coding 首页”。
3. 项目路径迁移应维护稳定 Location 身份或显式迁移记录，而不是只用可变绝对路径过滤 Session。正常首页至少把失效 Session 放入“需要重新关联”，不能静默计为 0。
4. 两个“新建会话”入口统一调用同一门禁：无 resolved 项目时 disabled 并说明原因；有项目时携带明确 `server + directory + mode=coding` 创建 Draft。不要保留可点击但无反馈的按钮。
5. Session Identity Header 必须显示模式、项目/目录、分支/Worktree、Agent、模型、权限和 Location 健康状态；这是阻止跨范围误判的安全边界，不只是视觉增强。

**续测判定：`PARTIAL / P1 LOCATION IDENTITY DEFECT`。** canonical URL、mode 水合和 Review 物理目录归属可达且正确，但 Location 别名没有归一化、项目登记已失效、正常入口静默丢失 Session；在项目与 Session identity 收敛前，写盘、PTY 和 provider-turn E4 结果仍可能无法从正常产品入口追踪。

### 19.3 各区域尚缺的关键反例

1. **Composer / Session**：provider 429/5xx、SSE 半包/断流、重复 completion、请求重放、busy 中 steer/queue、用户中断后恢复、reload/crash continuation、attachments/context payload。
2. **Files**：binary/large file、permission denied、path traversal、symlink、rename/delete、watcher update、并发写冲突、原子保存、Windows/UNC path。
3. **Terminal**：非零 exit code、SIGINT、异常 WebSocket 断开、server restart、外部 PTY discovery、孤儿进程回收、Windows shell 与 WSL。
4. **Work / Reviewer**：comment → fix request → response → resolved/reopen，候选稿多 revision、导出内容比对、CAS 冲突、取消/重试与回滚。
5. **Assistant**：提醒到期和 catch-up、重复投递抑制、失败重试、timezone/DST；memory/KB CRUD、搜索/引用、敏感信息及 personal/project scope 隔离。
6. **Custom**：发布快照不可变、旧 Session 保持旧 snapshot、升级/回滚、MCP 授权失败、capability 变化、执行崩溃恢复。
7. **Home / Route**：项目增删改、重复/失效/迁移目录、多服务搜索竞态与排序、server offline/recovery、unknown identity 明确失败。

### 19.4 建议的最小发布门禁

不建议继续把全业务套件机械复制到五个 presentation projects。更低成本且更健壮的分层门禁是：

1. 新增独立 **real-backend smoke project**：每次创建隔离 DB、临时 workspace 和可回收 PTY；禁止 `mockAigcfrogeServer`，结束后校验无残留 Session、文件和进程。
2. 使用项目内可控 LLM server/recorded deterministic provider 驱动流式响应、失败、断流和重试；只有经明确授权的环境才调用真实外部 provider，避免费用和数据泄露。
3. 五种产品模式至少各有 **1 条 happy path + 1 条 failure/recovery**；Custom 在真实 capability 未开放前保留 typed-gate 负向门禁，不伪造 E4 通过。
4. 基础 Chromium 业务套件先达到当前 **198/198** 且重复运行稳定；dark/zh/zht/narrow 只运行展示、布局、i18n、a11y 专项，避免 5 倍复制与顺序污染。
5. Linux 与 Windows 跑 Web real-backend smoke；Desktop 增加 Linux/Windows Electron smoke，并在可用 runner 上补 macOS packaged launch。原生 picker/update 等不可稳定自动化的部分保留版本化人工验收清单与证据。
6. 为 offline/reconnect、附件/导出、a11y、视觉与关键性能预算建立独立标签和 CI job；失败保留 trace、video、screenshot、backend log、临时 workspace manifest 和进程清理报告。
7. 建立 route × mode × layer × failure 的 coverage manifest。PR 只需跑受影响矩阵，主干/夜间跑完整真实集成；flake 必须有 owner、期限和预算，禁止用 retry 把不稳定误报为绿色。

### 19.5 当前发布判定

- **已验证**：大量 UI 状态机、路由、mock 请求契约、受限权限取消、草稿恢复、Settings Web 基础交互与持久化、部分 Work/Assistant/Custom 页面状态。
- **部分验证**：Work、Assistant、Reviewer、Home/Location、Files、Terminal、Session 执行；现有证据多数停留在 E3 contract，不是完整真实链。
- **未验证/被阻断**：真实 provider/SSE/tool/restart 生命线、真实文件与 PTY、Custom 真实运行、Electron/Desktop、offline/reconnect、附件与导入导出、自动 a11y、视觉基线、macOS。

因此发布结论继续保持 **CONDITIONAL**。在 P0 三项完成前，不应使用“端到端已闭环”或“可发布级 E2E 已完成”的表述。

## 20. 产品真实闭环余项与 Session 模式/自定义插拔模型（2026-09-13）

### 20.1 产品真实闭环还差什么

“页面可达”和“mock 交互通过”不是产品真实闭环。当前余项按阻塞关系收敛为四层：

1. **底层真实执行 P0**：建立 browser → real backend → durable `session_input` → provider/SSE → tool/result → terminal state → reload/recovery 的可重复 E4 自动链；补真实文件系统与 PTY 生命周期；取得当前 Chromium 198/198 且消除顺序污染。
2. **模式业务闭环 P1**：Work 完成 preset/澄清/产物 revision/保存导出/Reviewer/回滚；Assistant 完成 reminder 到期投递与重试去重、Memory/KB CRUD 和 personal/project 隔离；Custom 完成 plan/freeze/start/run/upgrade/rollback/archive；Home 完成 project/Location 增删改、失效恢复与多 server 一致性。
3. **失败与恢复 P1**：unknown server/Session/parent/malformed route fail closed；offline、SSE/WS 断流、慢网、乱序和重复事件恢复后幂等；附件、导入导出、权限/大小/类型失败可恢复。
4. **交付环境 P1/P2**：Electron IPC、原生 picker、deep link、menu/shortcut、通知、更新器、WSL、窗口和重启持久化；补 axe、屏幕阅读器抽检、视觉基线、性能预算和 macOS packaged smoke。

其中第 1 层是其余模式闭环的共同前提。若先继续为每个页面增加 mock 用例，会增加测试数量，但不会提升真实发布置信度。

### 20.2 当前 Session 如何区分固定模式

Session 的耐久身份以服务端记录为准，不以当前 URL、左侧选中态或 Agent 名称推断：

- `SessionV2.Info.mode` 是 `ProductMode.ID`；数据库 `session.mode` 为非空字段，默认 `chat`，并建立 project/directory + mode + updated time 索引。
- 当前固定枚举是 `chat | coding | work | assistant | custom`。App 的 `MODE_DEFINITIONS` 负责五个一级入口和 surface；打开已有 Session 后应以服务端返回的 `session.mode` 驱动页面，而不是沿用进入前的导航模式。
- 通用创建只允许 `chat/coding/work/assistant`。`custom` 在 `GENERIC_CREATION` 中明确为 false；调用通用 `/session` 创建 custom 会得到 typed `UnsupportedProductModeError`。
- 创建子 Session 时继承 parent 的 mode。普通模式由 `ProductModeAgentPolicy` 限制合法 primary Agent；例如 Chat/Work/Assistant 只允许 meta 或对应 orchestrator，Custom root 只允许 meta。
- mode 决定“产品策略和 UI 外壳”，但不能单独承担模型、权限或插件配置。模型、Agent、permission tier、Location 仍是独立字段，避免把所有语义塞入 mode 字符串。

建议将显示身份统一为：

```text
SessionIdentity =
  sessionID
  + productMode                  // chat/coding/work/assistant/custom
  + location                    // directory/workspace
  + agent + model source
  + permissionTier
  + customSnapshotRef?          // custom only: digest/profile/revision
```

Header、路由恢复、列表筛选和 capability gate 都消费同一个服务端投影，禁止分别推断。

### 20.3 当前 Custom 的插拔逻辑

当前架构已经选择了正确的基本方向：**Custom 不是不断扩展 `ProductMode.ID` 的新枚举值，而是一个稳定的 `mode="custom"` 容器；每个用户模式的差异由不可变 Composition Snapshot 表达。**

创建链如下：

```text
Custom Profile / Temporary Draft
  └─ agents + workflow + bindings(prompts/skills/commands)
     + presentation + requestedCapabilities
       ↓ resolve
Composition.Plan
  └─ digest + diagnostics + effective capabilities/MCP + cost preview
       ↓ expectedPlanDigest 校验并 freeze
Composition.Snapshot V1/V2
       ↓ 与 Session Created 在同一持久事务附着
Session(mode="custom", root agent="meta")
       ↓ 每次 provider turn 读取并校验 snapshot
按 consumer/agent scope 注入 instructions/prompts/skills/commands/tools/workflow
```

关键不变量：

- `createCustom` 必须原子地创建 Session 与 snapshot；不能先建空 custom Session 再逐项挂插件。
- `session_composition_snapshot` 以 `session_id` 为主键，保存 version、digest、profile path/revision 和 JSON data；已有 Session 的 snapshot 是执行真源。
- Provider turn 对 Custom fail closed：snapshot 缺失/损坏、tool 不存在、fingerprint/placement/installation version/catalog digest 漂移均产生 typed `SnapshotDriftError`，不能退回完整工具注册表。
- Snapshot V2 通过 agent/consumer scope 决定每个 Agent 能看到的 instructions、skills、commands 和 bindings，防止多 Agent 组合互相泄漏资产。
- Custom capability 由 server kill switch 和 `x-aigcfroge-capabilities: custom-v1` 双门禁控制；当前真实 4096 仍关闭，因此 UI 正向 mock 不代表运行可用。
- 升级不是原地修改 snapshot。`upgradeCustom` 要求源 Session idle，重新 freeze 并创建新 Session；旧 Session 与旧 snapshot 保持可重放。这比运行中热插拔安全。

### 20.4 后期“插拔”应如何定义

这里需要区分两类插拔：

1. **推荐：版本化插拔（Session 之间）**。用户修改 Agent/Skill/Prompt/Command/Workflow/MCP 后生成新 Plan 和 digest，发布新 Profile revision；新 Session 绑定新 snapshot，旧 Session 保留旧 snapshot。这是当前架构已经支持的方向。
2. **不推荐：运行中热插拔（同一 Session 内）**。直接改变活动 Session 的工具或指令会破坏历史可重放性、权限审计、tool-call schema 和 provider continuation。若未来业务必须支持，应把它建模成明确的 `CompositionEpoch` 边界：等待 Session idle → freeze 新 snapshot → 持久化 epoch 变更事件 → 下一 provider turn 使用新 epoch；不得静默改 registry。

每个可插拔资产至少需要：稳定 kind/id、revision、content digest、兼容 schema、capability/permission 声明、依赖与冲突、来源/签名、迁移策略和生命周期状态。MCP 还必须区分“声明请求”“用户授权”“健康可用”三种状态，不能因安装即自动获得权限。

UI 上一级导航仍只有固定 `Custom`；N 个自定义模式应作为 Profile/Release 列表展示，而不是动态向 ModeSwitcher 注入 N 个顶级 mode。打开自定义 Session 时显示 profile 名称、release/revision、snapshot digest、健康/漂移状态和 Upgrade 入口。

### 20.5 该架构尚未闭环的关键点

1. 真实 Custom capability 仍被关闭，尚无 E4 plan → freeze → start → provider turn → restart → replay 证据。
2. Profile 的 draft/release/archive/rollback 产品生命周期和旧 snapshot 保留策略尚未完成真实 UI 闭环。
3. `presentation` 已进入 composition input，但动态 surface/slot 的扩展协议、版本兼容和未知组件降级规则仍需明确；不可允许用户资产注入任意前端代码。
4. MCP auth、capability grant、permission tier、tool fingerprint drift 的真实失败恢复没有浏览器闭环。
5. Upgrade 当前语义是“新建 Session”，UI 必须明确呈现新旧 Session 关系，不能让用户误以为原会话被原地升级。
6. Session Header 尚未稳定展示 mode + Location/scope + profile/release/snapshot + Agent/model source + permission/capability health，冷启动仍可能短暂挂载错误模式 surface。

建议下一阶段的实现顺序是：先统一 `SessionIdentity/CapabilityState` 投影和 Header，再开放隔离环境下的 Custom capability，随后完成一条真实 `plan → start → run → restart → replay → upgrade` 金丝雀链，最后再扩展 Profile 管理和更多可插拔资产。

### 20.6 代码复核勘误（2026-09-13）

本节只纠正 §20.2–§20.3 的两个静态事实，不改写前述 E3/E4 证据与 CONDITIONAL 发布结论：

1. §20.2 中“数据库 `session.mode` 默认 `chat`”不准确。当前 `packages/schema/src/product-mode.ts` 的 `ProductMode.Default`、`packages/core/src/session/sql.ts` 的列默认值，以及 Session schema 的 constructor/decoding default 均为 **`coding`**。历史缺失 mode 的兼容解码也落到 Coding。
2. §20.3 中 capability 值 `custom-v1` 是简称，不是当前协议字面值。当前请求头为 `x-aigcfroge-capabilities`，值为 **`product-mode-custom-v1`**。

Custom 仍是已实现但默认受 `AIGCFROGE_CUSTOM_MODE` kill switch 关闭的第五 Product Mode；“已实现”不等于真实 4096 已启用，也不改变 §19.5 的 CONDITIONAL 判定。
