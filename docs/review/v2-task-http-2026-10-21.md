## 行为与决定规则

| Owner                            | 行为与关系依据                                                                                                                                                                                                                                                                                                          |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `SessionTask.updateTask`         | `packages/core/src/session/task.ts:980` 在既有进程写锁内读取 Session-scoped 行，先校验 expect 和 expectedRevision，再校验显式 status 的 schedule，最后执行一次 SQL update 和一次事件对。组合 status/content/priority/outputDigest 只增加一次 revision；非法 schedule、缺失与陈旧写入不改字段、digest、revision 或事件。 |
| `SessionTask.patch`              | `packages/core/src/session/task.ts:944` 适配同一 updateTask。既有执行 claim 的 expect 与 CAS 仍在公共写边界；`DelegationExecution.writeback`（`execution.ts:277`）沿用 admission 保存的父 Task revision。字段编辑后较早 claim 不能覆盖新 revision。                                                                     |
| `TaskUpdateTool`                 | `packages/core/src/tool/task-update.ts:78` 调用一次 updateTask，映射预期 typed 错误；defect 与 interruption 沿用 Tool 边界。工具及 HTTP 拒绝空编辑；Core 无字段调用保留原 touch 行为。                                                                                                                                  |
| `SessionTaskHttp.requireSession` | `packages/server/src/handlers/session-instance-stubs.ts:27` 读取 Session，并以 `locationRefForRoute`（`middleware/workspace-routing.ts:18`）同时解析 route 与持久 owner；同时比较 directory 与 workspaceID。未知 Session、跨 Location 及缺失/foreign 单行返回 404。                                                     |
| HTTP PATCH                       | `packages/server/src/handlers/session-instance-stubs.ts:56` 先检查存在/空编辑/已读 revision，再把 expectedRevision 传入 Core 锁内 CAS；CAS 未命中后重读以区分删除 404 与冲突 400。TaskWriteError 映射 InvalidRequestError 400。                                                                                         |
| HTTP CRUD                        | handler `:44`/`:50`/`:87`/`:97`/`:105` 分别复用 update/get/append/removeTask/reorder。`SessionTask.append`（`task.ts:789`）在事务内按最大 position 插入并读取本次列表，返回最后项是本次 append 的任务；并发后续 append 不改变该返回值。                                                                                 |
| 全量、digest 与 DAG              | `SessionTask.update` 的列与 digestById 规则（`task.ts:584`）保留省略的关联、schedule、spawn、dependsOn 和内部 digest；`TaskDag.findCycle`（`task.ts:530`）决定跨 Session 依赖是否成环。HTTP 写契约不接收 outputDigest；实际回归证明额外 digest/revision 输入不能覆盖内部值。                                            |
| Server 装配                      | `packages/server/src/routes.ts:71` 把 SessionTask.node 加入 applicationServiceNodes，复用 Database/Bus 依赖，供生产 handler 获取服务。                                                                                                                                                                                  |

状态未显式更新时不重验历史 invalid cron，保留既有字段编辑行为；显式回到 scheduled 必须通过 schedule 验证。CRUD 不准入 Session 输入、不改变 Session execution 状态，也不写 Assistant ScheduleTable。Custom mode 的记录管理沿用当前 CRUD 合同。

方案对冲：在 Tool/HTTP 各做两次写入容易产生部分提交；新建独立事务服务会增加 owner。本切片归并现有 patch 与 updateTask，并复用原进程写锁、SQL、Bus 和生成客户端。全量 reconcile 无 expectedRevision，reorder 的最大行 revision 也不能决定所有结构竞争；这些既有合同限制已登记，不宣称新增全量 CAS。
