## 3. 共同前提缺口：proposal 事实未进入持久 Tool 结果

当前 proposer 在 [65 行](/home/keer/workspace/aigcfroge-v2/packages/core/src/tool/propose-skill-asset.ts:65) 返回 machine `output` 与说明 `content`，没有 metadata。[ToolRuntime 55 行](/home/keer/workspace/aigcfroge-v2/packages/core/src/tool/runtime.ts:55) 分别编码 output 与规范化 content；决定规则 [normalizeContent](/home/keer/workspace/aigcfroge-v2/packages/core/src/tool/runtime.ts:261) 优先保留显式说明文本。[publish-llm-event.toolExecution](/home/keer/workspace/aigcfroge-v2/packages/core/src/session/runner/publish-llm-event.ts:579) 只将 content 与已有 metadata 发入 canonical `Tool.Success`。当前 [completed Tool state](/home/keer/workspace/aigcfroge-v2/packages/schema/src/session-message.ts:139) 也没有独立 output 字段。

因此读取持久 Session 消息的候选 UI 拿不到结构化 `relativePath`、`exists`、`revision`、`nameConflict`、`pathConflict`。这由通用 normalization/publisher 的持久边界决定，不能靠搬 UI 补齐。本文确认选中 producer 的缺口；其他族须逐个检查其 producer，不推断七个都相同。

旧 [proposer metadata](/home/keer/workspace/aigcfroge/packages/aigcfroge/src/tool/propose-skill-asset.ts:47) 明确保存上述事实；旧 [normalizeProposeCandidate](/home/keer/workspace/aigcfroge/packages/app/src/components/chat/prompt-asset-candidate.ts:235) 从 structured/metadata 读取，并在缺失时默认 `exists=false`、冲突为 false、`revision=null`。直接搬这个默认逻辑会把未知事实当成新资产。

最小修复建议是在现有选中 Tool 的 `metadata` 中持久化同一 proposal 事实，沿原有 `Tool.Success` 投影送达 UI。UI 严格检查 metadata 完整性，并与同一 tool input 配对；缺失、损坏或已变更候选不得以默认 facts 开启 apply。候选等价关系可复用旧 [sameCandidateInfo](/home/keer/workspace/aigcfroge/packages/app/src/components/chat/prompt-asset-candidate.ts:281) 的实际字段比较，按当前 Schema 适配。无需泛化存储所有任意 output，无需新建 proposal HTTP endpoint。
